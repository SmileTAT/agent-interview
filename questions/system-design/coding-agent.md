# 设计一个代码助手 Agent（仓库级 Coding Agent）

<QuestionMeta />

## 题目

设计一个仓库级编码 Agent：接收需求或 issue，在真实代码库中定位、修改、验证并提交 PR。请给出整体设计。

::: details 参考答案（作答框架）

**1. 需求澄清**：目标任务分布（bug 修复/小功能/重构占比）？仓库规模与语言栈？验证基建现状（测试覆盖、CI）？人审环节在哪（PR review 是底线）？

**2. 核心认知（决定架构的判断）**：编码 Agent 的质量上限由**验证闭环**决定——代码是可验证性最好的领域（编译、测试、lint），架构必须让 Agent"每改必验、以验促改"，而不是一次性生成大段代码。

**3. 架构：探索 → 计划 → 编辑-验证循环 → 交付**

- **代码理解层**：仓库太大不能全塞上下文——按需探索（grep/文件树/符号跳转做成工具），让 Agent 像人一样"顺着线索找"，配合可选的代码检索索引；
- **执行环境**：完整的沙箱开发环境（可装依赖、跑测试、跑 lint），文件系统与网络按沙箱标准隔离——Agent 写的代码是不可信代码；
- **编辑-验证循环**：小步修改 → 立即跑相关测试/静态检查 → 失败信息喂回下一轮（这是 Reflexion 的最佳实践场）；测试先行策略（先写复现失败的测试再修）显著提升 bug 修复可靠性；
- **交付层**：生成 PR（变更说明、测试证据、影响面自述），人审合入——Agent 不直接推主干。

**4. 关键设计点**：上下文管理（只读相关片段，长任务用结构化笔记记录已探索结论）；步数与时长预算+卡死检测；多任务并行时的环境隔离（每任务独立沙箱/worktree）。

**5. 评测**：SWE-bench 类端到端基准做能力基线 + 自有仓库的历史 issue 回放集（更真实）；指标：任务解决率、PR 一次通过率、人工返工程度、成本/任务。

:::

## 评分维度（rubric）

| 维度 | 合格 | 优秀 |
|------|------|------|
| 验证闭环 | 提到跑测试 | "小步改+即时验证+错误回喂"的循环设计，测试先行策略 |
| 代码理解 | 提到检索/索引 | 按需探索工具集的设计，说清为什么不全量塞上下文 |
| 沙箱安全 | 提到隔离 | 文件/网络/资源多维隔离+"Agent 代码即不可信代码"的意识 |
| 交付流程 | 生成代码即交付 | PR+人审+测试证据的完整交付契约 |
| 失败处理 | 提到重试 | 卡死检测、预算触顶的降级（提交部分进展+说明） |
| 评测 | 提到基准 | 公开基准+自有 issue 回放集双轨 |

## 追问链

::: details 追问 1：仓库没什么测试覆盖，验证闭环立不起来怎么办？

分级降级：静态层兜底（编译/类型检查/lint 至少保证"不明显坏"）；让 Agent **为自己的改动补测试**（改哪补哪，顺便沉淀资产）；关键路径用运行时冒烟验证（起服务打请求）；同时如实降低自主度——验证弱的仓库，Agent 产出定位为"高质量草稿"，人审权重加大。还可以反向立项：让 Agent 先做"补测试"类任务本身，既是安全的练手场又改善后续所有任务的验证基建。

:::

::: details 追问 2：Agent 改一个 bug 引入了两个新 bug（改动的涟漪效应），怎么控制？

多层：**影响面分析**进入流程——改动前让 Agent 显式列出调用方与影响范围，作为验证范围的依据；回归测试跑影响面而不只是改动点；**改动最小化**作为硬性风格要求（禁止顺手重构，重构是独立任务）；PR 里强制"影响面自述"供人审核对。评测上把"引入回归率"作为与解决率并列的核心指标——只考解决率会激励大刀阔斧的危险改法。

:::
