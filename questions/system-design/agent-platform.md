# 设计一个企业级 Agent 平台（多租户 Agent 运行时）

<QuestionMeta />

## 题目

公司多个业务团队都在自建 Agent，重复造轮子且安全参差。设计一个统一的 Agent 平台：业务团队在其上构建、部署、运营自己的 Agent。

::: details 参考答案（作答框架）

**1. 需求澄清**：业务团队的技术水平分布（要低代码还是纯代码）？现存 Agent 的框架多样性（迁移还是接纳）？安全合规的统一要求？平台团队规模（决定平台野心）？

**2. 平台的分层能力（core 与可选要分清）**

**必须统一的（平台核心价值）**：

- **模型网关**：统一接入多供应商模型——配额与限流调度、成本核算到团队、缓存策略、模型版本锁定与灰度、故障切换。这是 ROI 最高的一层，先做它；
- **工具/连接器注册中心**：企业系统的工具以 MCP Server 形态注册，统一鉴权（on-behalf-of）、权限审批流、审计——一次接入全平台复用；
- **安全基线**：凭证管理（不入上下文）、沙箱执行服务、注入防护组件、写操作分级与 HITL 审批服务、全量审计；
- **可观测**：统一 trace 规范（OTel）与存储、成本/质量看板、告警。

**弱约束的（契约而非实现）**：Agent 编排框架不强制统一——定义部署打包规范、trace 接入、评测接入的**契约**，业务团队框架自选（见 build-vs-buy 一题的治理思路）。

**3. 运行时设计**：Agent 作为受管工作负载部署（容器/函数），执行层带队列与 checkpoint 支持长任务；**多租户隔离**——团队间的配额、数据、凭证、沙箱全隔离，一个团队的失控任务不能拖垮平台（预算硬顶+熔断）。

**4. 生命周期治理**：Agent 上线要过的门——评测集与通过线（平台提供评测基建，用例业务自建）、安全 checklist（权限申报、写操作分级）、灰度发布支持;上线后的成本与质量周报自动生成。

**5. 平台成功指标**：业务 Agent 的上线周期（平台前 vs 后）、平台承载的 Agent 数与调用量、安全事故数、单位成本趋势；**采用率是真考卷**——平台没人用就是失败，哪怕架构再好。

:::

## 评分维度（rubric）

| 维度 | 合格 | 优秀 |
|------|------|------|
| 分层判断 | 罗列了能力 | 分清"必须统一/契约约束/业务自决"三档，说得出为什么 |
| 模型网关 | 提到统一接入 | 配额调度、成本归集、版本治理、故障切换成体系 |
| 安全体系 | 提到权限 | 凭证/沙箱/HITL/审计的平台化，安全是平台强制项 |
| 多租户 | 提到隔离 | 配额、故障、数据多维隔离+失控熔断 |
| 治理流程 | 有上线审批 | 评测门禁+灰度+运营周报的生命周期闭环 |
| 平台思维 | 建完即成功 | 采用率导向：迁移成本、自助体验、和业务共建的路径 |

## 追问链

::: details 追问 1：业务团队说"平台太重了，我们自己两周就能上线"，怎么让平台被用起来？

强推是下策，正确路径：**从最痛的点切入**——模型网关（配额和账单是每个团队的真痛点）几乎零迁移成本就能接，先让所有人用上这一层；**降低增量接入成本**——trace/评测/工具逐层可选接入，每层都独立有收益；**安全用政策兜底**——凭证与写操作规范是公司政策而非平台功能，不接平台也要满足，而平台是满足它的最低成本方式；**标杆共建**——和一两个头部业务深度共建打样，用他们的效率数据说话。平台的本质是产品，用户是内部工程师，产品思维照用。

:::

::: details 追问 2：平台上某个 Agent 出了安全事故（越权外发数据），平台和业务的责任边界怎么划？

事前就要划清，用"共享责任模型"（类比云厂商）：**平台责任**——基础设施层的保证（凭证不泄露、沙箱不逃逸、审计不缺失、HITL 服务可用）；**业务责任**——Agent 的行为设计（工具选择与权限申报的准确性、提示质量、评测覆盖）；**共同机制**——上线门禁是双方签字、事故复盘定位到层。技术上平台要能自证：完整审计链能还原"事故动作经过了哪些平台防线、为何放行"（如业务申报的权限范围内）。没有清晰责任模型的平台，出一次事故就会陷入"甩锅循环"并失去信任。

:::
