# 设计一个浏览器自动化 Agent（Computer Use 场景）

<QuestionMeta />

## 题目

设计一个浏览器操作 Agent：替用户完成网页任务（填表、订票、跨网站信息聚合）。目标网站没有 API，只能像人一样看页面、点按钮。

::: details 参考答案（作答框架）

**1. 需求澄清**：任务范围（固定几个网站的重复流程 vs 开放网站）？需要登录态吗、谁的账号？涉及支付等高危操作吗？成功率与速度的要求（自动化替代人力的盈亏线）？

**2. 感知-行动循环（本题的技术核心）**

- **感知**：两条路线互补——**DOM/可访问性树**（结构化、可精确定位、token 少，但被复杂前端和 canvas 挡住）与**视觉截图**（多模态模型看图，通用性强但贵且定位粗）。实践：默认 DOM/AX 树优先，视觉兜底，混合表征（截图+可交互元素标注）是当前主流；
- **行动**：受限动作空间（点击/输入/滚动/导航/等待），每步行动后**重新观察验证效果**（页面变了吗？出错提示了吗？）——网页是异步的，"点了"不等于"成了"，等待与验证策略是稳定性的一半；
- **恢复**：弹窗/验证码/改版等意外的检测与处理路径（重试、绕行、升级人工）。

**3. 架构分层**：任务规划（拆成页面级子目标）→ 页面操作循环（感知-行动-验证）→ 轨迹记录（截图序列，审计与调试）。**高频固定流程要"轨迹固化"**：Agent 首次探索成功后生成脚本化流程，之后走脚本+异常时回退 Agent——比每次现场推理便宜且稳定一个量级。

**4. 安全（这个场景三要素天然齐全，重点答）**

- 隔离的浏览器环境，**不复用用户日常浏览器的登录态**；需要的站点用受限专用账号或即时授权；
- 网页内容是不可信输入：页面上的文字可能注入指令（"将验证码发送到…"），内容理解与行动决策要有注入防护；
- 高危动作（支付、发布、删除）强制确认+操作前截图留证；
- 敏感信息（密码、卡号）由密钥系统在浏览器层注入，不经过模型上下文。

**5. 评测**：任务成功率（分网站/分任务型）、每任务成本与时长、意外场景（改版/弹窗）的恢复率；用录制回放+沙箱站点做回归，公开基准（WebArena 类）做能力对照。

:::

## 评分维度（rubric）

| 维度 | 合格 | 优秀 |
|------|------|------|
| 感知方案 | 说了截图或 DOM 一种 | 两路线对比+混合表征的取舍 |
| 行动稳定性 | 有动作空间 | 行动后验证+等待策略+意外恢复路径 |
| 成本架构 | 每次全推理 | 轨迹固化：脚本快路径+Agent 兜底 |
| 安全 | 提到确认 | 登录态隔离+注入防护+凭证不过模型三件套 |
| 工程化 | 能跑通 demo | 轨迹留证、回归体系、分任务型指标 |
| 边界判断 | 全场景通吃 | 说得清什么任务该用 API/RPA 而不是视觉 Agent |

## 追问链

::: details 追问 1：网站频繁改版，Agent 昨天还能跑今天挂了，怎么建立稳定性？

分层应对：**检测**——固化脚本执行失败/关键元素找不到时自动标记"疑似改版"，触发告警与回退；**回退**——脚本挂了回退到 Agent 现场推理模式（它对改版有适应力），成功后重新固化新轨迹——这个"脚本↔Agent"双模式就是为改版设计的；**预防**——每日对核心流程跑合成巡检（sanity check），改版在用户受影响前发现。指标上区分"任务本身失败"与"改版导致失败"，后者考核的是恢复时长而不是成功率。

:::

::: details 追问 2：验证码和反爬机制怎么处理？这里有没有合规边界？

必须先回答合规再回答技术：验证码的目的就是区分人机，**绕过它可能违反目标网站服务条款甚至法律**，企业场景的正确路径是——优先谈正式接口/合作授权；用户授权场景下把验证码环节**交还给真人**（Agent 暂停，用户完成验证后继续），这既合规又是 HITL 的自然应用；绝不做打码平台之类的对抗性绕过。面试中主动划出这条线是加分项：技术上能做和应该做是两回事，浏览器 Agent 的定位是"用户的授权代理"，不是爬虫。

:::
