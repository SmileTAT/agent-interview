# 设计一个数据分析 Agent（自然语言查数与分析）

<QuestionMeta />

## 题目

为业务团队设计数据分析 Agent：自然语言提问（"上季度华东区退货率为什么涨了？"），Agent 查询数仓、做分析、产出图表与结论。要求防止查错数、防止拖垮数仓。

::: details 参考答案（作答框架）

**1. 需求澄清**：用户画像（会不会看 SQL）？数仓规模与表规范程度（有没有语义层/指标口径文档）？错误数字的业务代价？查询负载隔离的现状？

**2. 核心认知**：Text-to-SQL 的难点不在 SQL 语法而在**业务语义**——"退货率"的分子分母、"华东区"的口径、该用哪张表，这些不解决，模型只会生成"语法正确、口径错误"的查询。所以架构核心是**语义层**。

**3. 架构**

```
提问 → 意图澄清（口径歧义时反问，而不是猜）
     → 语义层检索（指标定义、表结构+字段注释、口径规则、示例查询）
     → 查询生成（优先调用预定义指标 API，兜底生成 SQL）
     → 受控执行（只读账号、行数/超时/扫描量限制、队列隔离）
     → 结果分析循环（异常值追问、下钻、对比——代码执行环境做统计与画图）
     → 产出（图表+结论+使用的口径与 SQL 附录）
```

**4. 关键设计点**

- **语义层优先**：核心指标封装为受控的指标查询工具（口径由数据团队审定），自由 SQL 只服务长尾探索——高频问题走"选择题"，不走"默写题"；
- **执行安全**：只读专用账号（权限最小化）、资源隔离（独立队列/限流，防 Agent 生成全表扫描拖垮数仓）、查询前 dry-run/explain 预估成本，超阈值改写或拒绝；
- **正确性防线**：生成的 SQL 与口径**透明可审**（附录展示）；关键数字与已有报表对账（发现口径漂移）；多步分析用代码执行环境（pandas 类）而不是让模型"心算"统计；
- **归因类问题**（"为什么涨"）：结构化下钻框架（维度拆解→贡献度分析→关联变更），产出"主要由 X 细分贡献"而不是编叙事。

**5. 评测**：标注的（问题→正确口径与数值）评测集测数值正确率；SQL 成本合规率；用户侧盯采纳率与"与报表对不上"的投诉率。

:::

## 评分维度（rubric）

| 维度 | 合格 | 优秀 |
|------|------|------|
| 语义鸿沟 | 意识到口径问题 | 语义层/指标工具优先、自由 SQL 兜底的分层 |
| 执行安全 | 只读账号 | 资源隔离+成本预估+限额的完整防线 |
| 正确性 | 展示 SQL | 口径透明+报表对账+统计走代码执行 |
| 交互设计 | 直接出答案 | 歧义反问机制、结论带口径说明 |
| 归因分析 | 给出图表 | 结构化下钻框架，区分相关与因果 |
| 评测 | 有正确率概念 | 数值正确率评测集+口径漂移监控 |

## 追问链

::: details 追问 1："为什么涨了"这类归因问题，Agent 很容易给出看似合理的错误因果解释，怎么约束？

把归因约束在**可计算的部分**：维度贡献拆解（哪个子群贡献了多少涨幅）是算术，可以放心自动化；"为什么这个子群涨"的因果叙事必须降级处理——只呈现时间上关联的事实（"同期该区域上线了新退货政策"，来源是变更记录），标注为"相关线索"而非结论，因果判断留给人。提示与输出模板中强制区分"数据显示"与"可能解释"两个区块。数字可以自动，故事必须谨慎——这是数据产品的职业操守，也是这道追问的考点。

:::

::: details 追问 2：业务方拿 Agent 的数字和 BI 报表对不上，信任崩塌，怎么办？

技术+机制双修。技术：优先复用报表同源的语义层/指标 API（同源则天然一致）；不可复用处建立"口径对账"回归——评测集里放报表已有的问题，数值必须一致。机制：每个数字附口径与 SQL（可解释是信任的基础）；不一致案例的响应流程（快速归因是口径差异还是 bug，公示结论）；试运行期定位为"报表的补充"而非替代，用一致性记录逐步建立信任。信任是数据产品的核心资产，丢一次要用十次挽回。

:::
