# ReAct 范式是什么？相比让模型直接输出答案有什么优势？

<QuestionMeta />

## 题目

请解释 ReAct（Reasoning + Acting）范式的核心思想和执行流程，并说明相比让模型一次性直接输出最终答案，它解决了什么问题。

::: details 参考答案

**核心思想**：ReAct（Yao et al., 2022）让模型交替进行**推理（Thought）→ 行动（Action）→ 观察（Observation）**的循环：模型先显式写出当前的思考，再决定调用哪个工具（或给出最终答案），然后把工具返回的结果作为观察写回上下文，进入下一轮循环，直到得出最终答案。

**执行流程**：

```
用户问题 → Thought(分析要做什么) → Action(调用工具+参数)
        → Observation(工具返回) → Thought → Action → … → Final Answer
```

**相比直接输出答案的优势**：

1. **接入外部世界**：模型参数中没有的信息（实时数据、私有库）通过工具获取，减少幻觉；
2. **推理落地为行动**：显式 Thought 让模型"先想后做"，行动由推理驱动，而非模式匹配式地乱调工具；
3. **可纠错**：每轮观察后可以根据结果调整策略——工具报错、结果不符合预期时能换个思路重试；
4. **可解释可调试**：Thought/Action/Observation 轨迹就是天然的调试日志，工程上便于做轨迹级评测和问题定位。

**一句话对比**：直接输出是"闭卷考试一次作答"，ReAct 是"开卷考试，边查资料边验证边写"。

:::

## 追问链

::: details 追问 1：ReAct 有什么局限？生产环境中你会担心什么？

- **延迟与成本**：每一步都要完整推理一次，多轮循环叠加，token 消耗和响应时间随步数线性增长；
- **容易死循环/漫游**：目标不明确时反复调用同一工具或在无关路径上打转（需要 max_iterations、循环检测兜底）；
- **上下文膨胀**：长任务中 Observation 不断累积，可能挤爆上下文窗口、稀释关键信息；
- **短视规划**：每步只看当前状态做局部决策，缺乏对整个任务的全局拆解。

:::

::: details 追问 2：那 Plan-and-Execute 模式是怎么解决这些问题的？两者怎么选？

Plan-and-Execute 先让一个规划器一次性生成完整任务计划（步骤列表），再由执行器逐步执行，必要时重新规划。

- **优势**：全局视角、可用小模型执行降低成本、步骤可并行；
- **劣势**：计划赶不上变化——环境反馈频繁推翻计划时，重规划开销反而更大。

**选型经验**：任务结构清晰、步骤可预知（如数据处理流水线）→ Plan-and-Execute；探索性强、每步依赖上一步结果（如深度调研、排错）→ ReAct；实践中常用混合：先粗粒度规划，步内用 ReAct。

:::

::: details 追问 3：怎么减少 ReAct Agent 的无效循环？

- **预算控制**：max_iterations / token 预算 / 超时，触顶后强制收敛或转人工；
- **循环检测**:连续 N 次相同（工具，参数）调用直接拦截并注入提示；
- **反思步（Reflection）**：每 k 轮插入一次"当前进展是否偏离目标"的自评；
- **工具返回质量**：让工具在失败时返回结构化、可指导下一步的错误信息（而不是裸异常文本）；
- **终止条件显式化**：在系统提示中明确"什么情况下应该给出最终答案/承认无法完成"。

:::

::: details 追问 4：推理模型（如 o 系列、R1）普及后，还需要显式的 ReAct 提示结构吗？

需要的程度在下降，但循环本身没有消失。推理模型把 Thought 内化到了思维链里，主流 API 已原生支持"思考 + 工具调用交替"（interleaved thinking），不再需要用提示词模板手工约束 Thought/Action 格式。但工程层面的东西不变：工具 schema 设计、观察结果回填、预算控制、轨迹记录仍然是 Agent 循环的骨架——ReAct 作为**提示技巧**在退役，作为**架构模式**仍是事实标准。

:::
