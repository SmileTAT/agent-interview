# Agent 循环的预算与终止条件应该怎么设计？

<QuestionMeta />

## 题目

一个生产级 Agent 循环需要哪些预算与终止机制？分别防什么问题？

::: details 参考答案

终止分两类：**正常终止**（模型自己判断任务完成）和**强制终止**（预算护栏触发）。生产系统两者都要有，且强制终止必须优雅。

**正常终止的设计**：

- 终止判据写进系统提示：什么算完成、什么情况应承认无法完成——模糊的完成标准是"永远觉得信息不够"型死循环的根源；
- 提供显式的"提交最终答案"工具或输出通道，让终止成为模型的一个明确动作而非隐式行为。

**强制终止的预算矩阵**：

| 预算 | 防什么 |
|------|--------|
| 最大步数 / 递归深度 | 死循环、任务漫游 |
| 单会话 token 预算 | 成本失控（步数少但每步巨大的情况） |
| 墙钟超时 | 慢工具堆积导致的延迟失控 |
| 单工具连续失败次数 | 在坏工具上反复撞墙 |
| 重复调用检测 | 相同（工具+参数）的无效循环 |

**关键设计点：预算触顶≠硬失败。** 触顶后应进入收尾流程——给模型最后一轮机会（注入"预算已尽，请基于已有信息给出最佳答案或说明未完成原因"），输出部分结果+进展摘要，比直接抛异常对用户友好得多，摘要还能支持人工接手或断点续跑。

**预算取值**：不拍脑袋，用线上成功轨迹的步数/token 分布（P95~P99）定初值，按任务类型分层配置，随数据迭代。

**答题关键**：区分两类终止 + 多维预算矩阵 + "优雅收尾"意识。

:::

## 追问链

::: details 追问 1：模型"提前终止"（任务没完成就说完成了）怎么办？这和死循环哪个更难处理？

提前终止更隐蔽也更难：死循环有明确信号（步数、重复），假完成需要质量检验才能发现。手段：完成前的自检步（对照任务要求逐项核对）、关键任务用独立 critic 验收、评测集中专门构造"容易半途而废"的多步任务盯住这个指标。根因常在提示：完成标准写得太松，或历史对话里有"快速响应"的隐性激励。

:::

::: details 追问 2：长任务(几小时级)的预算设计有什么不同？

单会话预算模式失效，要改成**分段+检查点**：任务拆为多个阶段，每阶段独立预算；阶段间持久化进度（已完成步骤、中间产物、下一步计划），既支持断点续跑，也让预算触顶的损失只限于当前段。同时增加"进度检测"——连续 N 步没有产生新的中间产物即视为停滞，触发重规划，而不是等总预算烧完。

:::

::: details 追问 3：用户中断（用户主动喊停）算终止条件吗？要怎么处理？

算，而且是最高优先级的终止信号，工程上却常被忽略。要求：循环的每一步之间检查取消信号（而不是一步内不可中断）；中断时正在执行的写操作要能安全收尾（完成或回滚，不能留下半态）；中断后保留轨迹和进度摘要，用户可能只是想改个方向再继续。流式架构下这就是"中断恢复"能力的一部分。

:::
