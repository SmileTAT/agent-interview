# Agent 的错误恢复应该怎么设计？

<QuestionMeta />

## 题目

Agent 在执行中会遇到工具报错、结果不符合预期、模型输出格式错误等各种失败。请系统地说明错误恢复的设计方法。

::: details 参考答案

先分类，再对症——错误恢复设计的第一步是**给错误分层**：

**1. 瞬时性错误**（网络抖动、限流、超时）
→ 框架层自动重试 + 指数退避，对模型透明，不消耗模型推理。限流要读 Retry-After，重试要有上限。

**2. 格式类错误**（模型输出的工具参数不合 schema、JSON 解析失败）
→ 结构化输出约束（constrained decoding / strict schema）从源头减少；仍失败时把校验错误信息回传给模型重新生成，通常一次就能修复。

**3. 语义类错误**（工具正常返回但结果表明操作方向错了：查无此单、权限不足、搜索无结果）
→ 这是**必须让模型看到并处理**的一类：工具返回结构化错误（类型 + 原因 + 建议动作），模型基于观察调整策略。设计要点是错误信息要"可指导下一步"。

**4. 目标级错误**（走了几步发现整个方案不对）
→ 需要显式的反思/重规划机制：允许模型宣告"当前计划失败"，回滚到规划步，带着失败教训重新规划（Reflexion 思路）。

**兜底层**：所有恢复机制都有预算（重试次数、总步数、token 上限），预算耗尽进入降级动作——输出部分结果、承认失败、转人工。**Agent 系统的可靠性不在于不犯错，而在于每一层错误都有明确的去处。**

**答题关键**：分层分类 + "哪层错误由代码处理、哪层交给模型"的边界意识 + 永远有兜底。

:::

## 追问链

::: details 追问 1：哪些错误应该瞒着模型自动处理，哪些必须让模型知道？判断标准是什么？

标准是**这个错误是否应该影响模型的决策**。网络重试成功了，模型不需要知道（知道了反而浪费上下文、可能引发多余的"谨慎"行为）；权限不足、数据不存在这类错误携带了任务相关信息，必须让模型看到。反例是把限流错误传给模型——模型会"体贴地"等待或放弃，但它对限流其实无能为力，这该由代码层解决。

:::

::: details 追问 2：写操作失败后重试，怎么避免重复副作用（比如重复下单）？

幂等设计：客户端生成幂等键（idempotency key）随写请求提交，服务端对同键请求去重；工具返回明确的执行凭证（订单号），让模型能先查状态再决定是否重试。原则是"**不确定是否成功时先查询、绝不盲重试**"——这个规则要写进工具描述和系统提示，同时在工具层硬约束（同一幂等键拒绝二次执行）。

:::

::: details 追问 3：怎么评测一个 Agent 的错误恢复能力？

主动注入故障做混沌测试：评测集中构造工具超时、返回错误、返回误导性结果的用例，考察 Agent 是否按预期路径恢复（换策略/降级/转人工）而不是死循环或幻觉。指标：故障场景下的任务完成率、恢复所用额外步数、错误处理路径的命中率。这类"坏天气用例"应该占回归集的相当比例——晴天人人会飞。

:::
