# 什么任务不该用 Agent 来做？请给出你的判断框架

<QuestionMeta />

## 题目

面试官反向提问：大家都在讲 Agent 能做什么，请你讲讲什么任务**不该**用 Agent，并给出一个可操作的判断框架。

::: details 参考答案

一个实用框架是从四个维度打分，**任一维度不达标就应降级方案**：

**1. 任务价值 vs 运行成本**
Agent 每次运行消耗大量 token 和时间。价值低、频次高的任务（如简单分类、格式转换）用 Agent 是负 ROI——一次 LLM 调用甚至规则就够。

**2. 错误代价 vs 可验证性**
Agent 一定会犯错，问题是错误能不能被便宜地发现和撤销。**错误代价高且难验证**的任务（直接改生产数据库、对外发合同）不适合自主 Agent，至多做"Agent 起草 + 人审批"。错误便宜可逆（草稿、内部检索）才适合放开自主性。

**3. 路径可预知性**
流程固定的任务用 Workflow 更便宜可控（见 Agent vs Workflow 一题）。

**4. 反馈信号质量**
Agent 循环依赖环境反馈来纠偏。如果任务**没有可用的中间反馈**（无法验证的判断题、纯主观决策），Agent 的循环就是盲飞，多步只会积累偏差。

**典型不该用的场景**：高频低价值转换类任务（成本）、不可逆高危操作（风险）、强合规确定性流程（可预知+审计要求）、无反馈的开放判断（盲飞）、以及**延迟敏感的同步链路**（Agent 多轮循环天然慢）。

**答题关键**：给出维度化框架而非例子堆砌，并主动谈 ROI——这道题考的是工程判断力和成本意识。

:::

## 追问链

::: details 追问 1：老板就是要"全面 Agent 化"，你怎么落地这个判断框架？

把框架变成分级制度而不是否决制度：按上面四维给任务打分，分成"全自主 / 人在回路 / 仅起草 / 不适用"四档，每档配不同的护栏和验收标准。用一两个高分场景先做出可量化的成功案例，用数据（完成率、成本、事故数）反过来说服调整低分场景的期望。技术判断要翻译成风险和 ROI 语言。

:::

::: details 追问 2：错误代价高的任务就完全不能碰吗？

不是，是改变自主性形态：**压缩自主边界**（Agent 只做只读调研和方案起草，写操作由人执行）、**加确认层**（高危动作前 human-in-the-loop）、**提供可逆性**（操作先落到 staging/草稿态，确认后才生效）。核心思路是把"错误代价高"改造成"错误可拦截、可撤销"，而不是放弃自动化。

:::

::: details 追问 3：这个框架里哪个维度最常被团队忽略？

反馈信号质量。团队通常会评估成本和风险，但很少问"Agent 跑到第三步时，靠什么知道自己错了？"没有中间反馈的多步任务，错误会静默累积到最后才暴露，且无法归因。落地时应该反过来先设计反馈（测试、校验规则、中间产物检查点），反馈体系设计不出来，往往说明这个任务本身还不适合 Agent 化。

:::
