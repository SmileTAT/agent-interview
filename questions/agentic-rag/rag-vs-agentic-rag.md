# 传统 RAG 和 Agentic RAG 的本质区别是什么？什么时候不该用 Agentic RAG？

<QuestionMeta />

## 题目

请对比传统 RAG 与 Agentic RAG 的架构差异，并说明各自的适用边界——尤其是什么场景下**不应该**上 Agentic RAG。

::: details 参考答案

**本质区别：检索由"固定流水线"变成"模型的决策"。**

- **传统 RAG**：固定管道 `query → 检索 top-k → 拼上下文 → 生成`。检不检索、检索什么、检几次，全部在代码里写死，模型只负责最后的生成。
- **Agentic RAG**：把检索变成 Agent 的工具，由模型在循环中决策——**要不要检索**（简单问题直接答）、**查什么**（改写、拆解成多个子查询）、**去哪查**（多知识源路由）、**够不够**（评估检索结果，不够就换策略再查）、**信不信**（对检索内容做自我校验后再生成）。

**Agentic RAG 的典型收益场景**：多跳问题（需要先查 A 才知道该查 B）、多源异构知识库、query 与文档表述差距大需要多轮改写、对幻觉容忍度低需要自校验的场景。

**什么时候不该用**：

1. **延迟敏感**：Agentic 意味着多轮模型调用，首 token 延迟成倍增加——在线客服的高频简单问答用固定管道更合适；
2. **成本敏感 + 问题分布简单**：80% 的问题一跳就能答，为 20% 上全量 Agentic 不划算——正确做法是**分流**：简单问题走固定管道，复杂问题升级到 Agentic；
3. **检索本身很差**：召回质量不行时，Agentic 只是让模型反复在垃圾结果里打转，应先修检索基本功（分块、embedding、重排）；
4. **可控性要求极高**：固定管道行为可预测、易测试；Agentic 引入决策方差，合规场景可能不接受。

**答题关键**：说清"决策权从代码移到模型"这个本质，并主动给出否定性边界——面试官考察的正是工程判断力，而不是无脑上新架构。

:::

## 追问链

::: details 追问 1：怎么评测 Agentic RAG 比传统 RAG 好多少？

分层评测：**检索层**（context precision/recall——检回的内容是否相关、该检回的是否检回）、**生成层**（faithfulness——答案是否忠实于检索内容、answer relevancy）、**端到端**（人工标注的 golden set 上的正确率）+ **代价维度**（延迟、token 成本、检索次数）。关键是同一份评测集上跑 A/B，报告"质量提升多少、代价增加多少"，让业务方做权衡，而不是只报质量。

:::

::: details 追问 2：多跳问题上 Agentic RAG 还是查不好，你会怎么优化？

先看轨迹定位卡在哪一跳：**拆解错**（第一跳的子问题就提错了）→ 在提示中给多跳拆解的 few-shot、或引入显式的查询规划步；**中间信息丢失** → 把每跳的结论显式写入工作记忆而不是依赖原始检索内容堆积；**知识库结构不支持** → 考虑 GraphRAG，把实体关系显式建图，多跳变成图遍历而不是多轮向量检索。

:::

::: details 追问 3：检索回来的内容互相矛盾怎么办？

工程上分三步：**冲突暴露**——提示模型显式列出矛盾点而不是悄悄选一个；**优先级规则**——按来源权威度、时效性排序（如官方文档 > 社区帖子，新版本 > 旧版本，元数据里要有这些字段）；**降级动作**——无法裁决时在答案中并列呈现两种说法并标注来源，让用户判断。绝对要避免的是模型无声地混合两个矛盾来源生成一个"看起来自洽"的错误答案。

:::
