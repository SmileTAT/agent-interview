# GraphRAG 是什么？什么场景值得上，代价是什么？

<QuestionMeta />

## 题目

请解释 GraphRAG 的原理、相对传统向量 RAG 的优势场景，以及它的工程代价。

::: details 参考答案

**原理**：传统 RAG 把文档当作互相独立的块，**块与块之间的关系信息全部丢失**。GraphRAG 在索引阶段用 LLM 从文档中抽取实体和关系，构建知识图谱；（以微软 GraphRAG 为代表的实现还会）对图做社区检测，为每个社区预生成摘要。查询时不只做块检索，而是**沿图结构游走/聚合**来回答问题。

**两类它明显占优的问题**：

1. **多跳关系问题**："A 公司 CEO 投资过哪些和我们供应商有竞争关系的企业？"——向量检索没有任何一个块同时包含这条推理链，而图上这就是一次多跳遍历；
2. **全局归纳问题**："这批文档的主要争议点是什么？"——向量检索只能召回 top-k 个局部块，无法"看全局"；GraphRAG 用社区摘要自底向上聚合回答（global search 模式）。

**工程代价（必须如实评估）**：

- **索引成本高**：全量文档过 LLM 抽实体关系，token 成本可能是向量索引的几十倍以上，大语料上是真金白银；
- **抽取质量决定上限**：实体对齐错误（"阿里""阿里巴巴"没合并）、关系漏抽，图的错误会静默传导到答案；
- **更新维护难**：文档变更需要增量更新图结构与社区摘要，比向量索引的增删复杂得多；
- **查询路由复杂**：简单事实题走图反而绕远，需要路由层判断"这题走向量还是走图"。

**选型建议**：默认先做好"混合检索+重排"的基线；只有当 bad case 分析显示**多跳与全局归纳类问题占比可观**、且语料相对稳定（更新不频繁）时，GraphRAG 的投入才划算。混合架构（向量为主、图管关系类查询）是常见落地形态。

**答题关键**：说清"关系信息丢失"这个根因、两类优势问题、以及成本的量级感——面试官在筛"追新概念"还是"会算账"。

:::

## 追问链

::: details 追问 1：不上完整 GraphRAG，有没有轻量的办法吃到"关系"的收益？

有，几个中间态：**元数据关系**——文档间的显式关系（引用、父子、同项目）存为元数据，检索后沿关系扩展一跳（graph-lite）；**实体索引**——只抽实体不建全图，用实体共现把相关块连起来，多跳问题时按实体链式检索（Agentic 检索循环天然支持：查到 A 的 CEO 是 X，下一轮查 X 的投资）；后者其实就是**用 Agent 的多轮检索代替图遍历**——语料不大、跳数不深时，这比建图便宜得多。

:::

::: details 追问 2：图的抽取质量怎么保障和评测？

抽样人工标注建立抽取评测集（实体准确率/召回率、关系正确率、**实体对齐正确率**——重灾区），迭代抽取提示与对齐规则；上线后用"答案追溯"间接监控——错误答案回溯到图上，统计多少源于图错误。工程技巧：抽取时保留证据文本（每条边挂原文片段），既方便人工核查，也让生成阶段可以引用原文而不是只信图——图错误的最后一道缓冲。

:::

::: details 追问 3：什么信号说明你的场景其实不需要 GraphRAG？

倒排信号清单：bad case 里多跳/全局类问题占比很低（大多是单点事实没检到——那是召回问题）；语料更新频繁（图维护成本吃不消）；查询延迟预算紧（图查询+社区摘要链路更长）；团队没有持续维护图质量的人力。最常见的误判是把"检索质量差"误诊为"缺图谱"——先做检索基本功（分块、混合检索、重排）的提升，基线做满之后剩下的 bad case 才配得上讨论 GraphRAG。

:::
