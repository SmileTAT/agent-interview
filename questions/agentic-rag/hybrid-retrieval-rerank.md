# 混合检索与重排：为什么向量检索不够？完整的检索管线长什么样？

<QuestionMeta />

## 题目

为什么生产级 RAG 很少只用向量检索？请描述"混合检索 + 重排"的完整管线和各组件的作用。

::: details 参考答案

**向量检索的盲区**：embedding 擅长语义相似，但对**精确匹配信号不敏感**——产品型号（"XR-500"）、错误码、人名、专业术语缩写，语义向量常常抓不住这些"必须字面命中"的查询意图；且 embedding 对领域外词汇（新产品名）表现差。而这类查询在企业场景占比很高。

**混合检索管线（业界标准形态）**：

```
查询 → ①查询处理（改写/扩展）
     → ②双路召回：BM25（关键词）∥ 向量检索（语义）  [各取 top 几十]
     → ③融合（RRF 互惠排名融合，无需调权重）
     → ④重排（cross-encoder 对 query-块对精排）  [取 top 几个]
     → ⑤送入生成
```

- **BM25**：精确词匹配 + 词频统计，抓字面命中，补向量的盲区；零训练成本、可解释；
- **双路融合（RRF）**：按各路排名的倒数加总融合，对分数尺度不敏感，是最稳的默认选择；
- **重排器**：召回阶段模型（bi-encoder）为了效率牺牲了精度——query 和文档独立编码；cross-encoder 重排器把 query 与候选块**拼在一起**深度交互打分，精度显著更高但只能作用于少量候选。"粗召回 + 精重排"是搜索领域几十年的经典架构在 RAG 的复现。

**效果**：混合检索 + 重排相对纯向量，在多数企业评测集上召回与精度都有明显提升，是 RAG 优化投入产出比最高的一档（远高于换生成模型）。

**答题关键**：向量的精确匹配盲区 + 五段管线 + RRF 与 cross-encoder 的角色。

:::

## 追问链

::: details 追问 1：重排器增加了延迟，怎么权衡？

延迟增量 = 候选数 × 单对打分时间，控制手段：候选收窄（重排 top 20~50 而不是 200）、用轻量重排模型、批量并行打分。是否值得看场景：离线/异步任务无脑加；在线对话看质量收益——通常重排带来的精度提升允许你把送入生成的块数减半（省生成侧 token 和噪音），端到端算下来经常反而更快更省。用评测集量化"加重排 vs 不加"的完成率差再决定。

:::

::: details 追问 2：查询处理（改写/扩展）具体做什么？什么时候需要？

三类操作：**指代补全**——多轮对话里"它的价格呢"改写成完整查询（对话式 RAG 必做）；**查询扩展**——同义词、术语展开（HyDE 思路：让模型生成假设答案再用它检索，弥合问题与文档的表述差）；**查询分解**——复合问题拆成多个子查询分别检索。什么时候需要：看 bad case——检索失败的查询里如果大量是"表述与文档不匹配"或"一问多意"，就是查询处理的活；如果是字面匹配缺失，先加 BM25。

:::

::: details 追问 3：元数据过滤在管线里放哪？和语义检索怎么配合？

放在召回**之前或之中**（pre-filter）：先按硬条件（部门、时间范围、文档类型、权限！）过滤候选空间，再在子集内做语义检索——顺序反了（先检索后过滤）会出现"top-k 全被过滤掉"的空结果。权限过滤必须是硬过滤而且在检索层执行，绝不能靠生成阶段"提示模型别用无权内容"。Agentic RAG 里可以让模型生成过滤条件（从自然语言解析出时间/类型约束），但过滤的执行永远在引擎层。

:::
