# 文档分块（Chunking）策略怎么选？对 RAG 质量影响有多大？

<QuestionMeta />

## 题目

分块是 RAG 索引阶段最重要的决策之一。请对比常见分块策略，并说明选型与调优方法。

::: details 参考答案

**为什么分块重要**：块是检索的原子单位。块太大——一个块混多个主题，embedding 语义被稀释、检回一堆无关内容；块太小——上下文残缺（"该参数默认为 true"检回来却不知道说的是哪个参数）。大量 RAG 质量问题的根因在索引层而不是模型层。

**常见策略**：

1. **固定长度切分**（按 token 数+重叠）：实现最简单，但会拦腰截断句子和逻辑单元——仅适合无结构纯文本的快速起步；
2. **递归/结构感知切分**：按分隔符层级（标题→段落→句子）递归切，尽量在自然边界断开；对 Markdown/HTML/代码用格式结构（标题层级、函数边界）切——**默认推荐**，性价比最高；
3. **语义切分**：按相邻句子 embedding 相似度的骤降点断开，主题边界最干净，但索引成本高、提升不总是显著；
4. **父子块（small-to-big）**：用小块做检索（语义聚焦、召回准），命中后返回其所属的父块/邻域（上下文完整）——检索精度与上下文完整性兼得，长文档场景强烈推荐；
5. **上下文增强块**：给每个块附加元信息（文档标题、章节路径、一句块摘要——即 contextual retrieval 思路）再嵌入，缓解"块内容脱离文档语境后语义漂移"的问题。

**选型方法**：没有普适最优，**用自己的检索评测集调**——固定其他环节，只换分块策略跑 recall/precision；块大小从几百 token 级别起步做网格实验。文档类型异构时按类型用不同策略（FAQ 一问一答天然成块、合同按条款、代码按函数）。

**答题关键**：块是检索原子单位的认知 + 结构感知为默认、父子块为进阶 + 评测驱动调优而非拍脑袋。

:::

## 追问链

::: details 追问 1：表格、图片穿插在文档里，分块怎么处理？

多模态内容不能当纯文本切：**表格**——整表保留为一个块（截断的表格几乎不可用），并生成表格的文字摘要用于嵌入检索，命中后返回原表（结构化格式如 Markdown）；大表按行分片但每片都带表头。**图片**——用多模态模型生成图片描述入索引，或直接用多模态 embedding；图文关联要保留（图的块引用其所在章节）。核心原则：**嵌入用于"被找到"的表示，返回用于"被使用"的原文，两者可以不同**。

:::

::: details 追问 2：块的重叠（overlap）有什么用？设多少？

重叠防止关键信息恰好被切分线劈开（一句话前半在块 A 后半在块 B，两个块都检不到完整语义）。副作用是索引膨胀和检索结果重复。经验：结构感知切分下重叠可以很小（自然边界本来就少劈句子），固定长度切分才需要较大重叠兜底。用了父子块策略后重叠基本可以省——邻域返回已经解决了边界残缺。

:::

::: details 追问 3：知识库文档频繁更新，分块索引怎么维护？

增量更新而非全量重建：文档级版本追踪，变更文档的旧块删除、新块重嵌入；块 ID 设计成"文档ID+稳定序号"便于级联清理。两个坑：**删除遗漏**——文档删了向量还在，检索返回幽灵内容（务必级联删除+定期对账）；**新旧混检**——更新窗口期新旧块并存，给块带版本号且检索时过滤。分块策略本身升级时才全量重建，且新旧索引灰度切换、用评测集对比后再全切。

:::
