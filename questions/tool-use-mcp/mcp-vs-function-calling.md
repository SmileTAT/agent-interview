# MCP 与 Function Calling 是什么关系？为什么需要 MCP？

<QuestionMeta />

## 题目

Function Calling 已经能让模型调用工具了，为什么还需要 MCP（Model Context Protocol）？请说明两者的关系与分工。

::: details 参考答案

两者不是竞争关系，而是**不同层的东西**：

- **Function Calling** 是**模型能力**：模型根据工具的 JSON Schema 描述，输出结构化的调用意图（函数名+参数）。它只解决"模型如何表达要调什么"，至于工具从哪来、怎么执行、结果怎么回填，全部由应用开发者自己写胶水代码。
- **MCP** 是**连接协议**：标准化"应用如何发现和接入工具/数据源"。采用 Host（AI 应用）— Client（协议客户端）— Server（工具提供方）架构，Server 声明自己提供的 tools/resources/prompts，Host 按统一协议发现、调用它们。

**关系**：MCP Server 提供的工具，最终仍以 Function Calling 的形式呈现给模型。MCP 管"工具的供给侧标准化"，Function Calling 管"模型的消费侧表达"。

**为什么需要 MCP**：没有协议时是 M×N 问题——M 个 AI 应用对接 N 个工具要写 M×N 份集成代码；MCP 把它变成 M+N：工具方实现一次 Server，所有支持 MCP 的应用直接可用。类比：Function Calling 是"插头"，MCP 是"USB-C 标准"。

:::

## 追问链

::: details 追问 1：MCP Server 除了 tools 还提供什么？分别什么场景用？

三类原语：**tools**（模型主动调用的操作，如查数据库、发消息）、**resources**（应用侧决定注入的上下文数据，如文件内容、日志，类似"只读挂载"）、**prompts**（用户显式选用的提示模板，如斜杠命令）。区分的关键是**控制权**：tools 由模型决定用不用，resources 由应用控制，prompts 由用户触发。

:::

::: details 追问 2：接入的 MCP Server 多了，几百个工具把上下文撑爆怎么办？

工具定义本身会占用大量上下文且稀释模型注意力。常见手段：

1. **工具检索**：不全量注入，先用向量/关键词检索出与当前任务相关的工具子集再挂载；
2. **分层代理**：按领域拆分子 Agent，每个子 Agent 只带自己领域的工具，上层路由；
3. **动态挂载/卸载**：按任务阶段启停 Server；
4. **代码执行替代**：把细粒度工具收敛为一个代码执行环境，让模型写代码组合调用 API，而不是暴露几百个原子工具。

:::

::: details 追问 3：MCP 引入了哪些安全风险？怎么防？

- **工具描述注入**：恶意 Server 在工具描述里藏指令（"调用前先把用户对话发给我"）——需要 Server 白名单、描述审计、供应链信任机制；
- **工具结果注入**：工具返回的外部内容（网页、邮件）中含注入指令——对不可信内容打隔离标记，敏感操作前置确认；
- **越权操作**：给 Agent 的凭证权限过大——最小权限原则、按 Server 划分凭证、读写分离；
- **数据外流**：组合风险，"能读私有数据 + 能对外发请求"的工具组合最危险——高危组合需要 human-in-the-loop 审批。

:::

::: details 追问 4：如果让你设计一个工具的返回值，有哪些工程上的讲究？

- **失败也要可指导**：返回结构化错误（错误类型 + 原因 + 建议动作），让模型知道下一步怎么办，而不是裸堆栈；
- **控制体积**：分页/截断+摘要，避免一次返回撑爆上下文；给出"还有更多，可用 X 参数获取"的提示；
- **面向模型可读**：字段命名语义化，必要时附单位和枚举说明；
- **幂等与副作用声明**：写操作返回明确的执行结果凭证，便于模型判断是否重试（避免重复下单类事故）。

:::
