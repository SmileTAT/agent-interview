# 线上 Agent 反复调用同一个搜索工具十几次不终止，如何排查与修复？

<QuestionMeta />

## 题目

你负责的客服 Agent 上线后，监控发现部分会话中 Agent 连续调用同一个知识库搜索工具十几次仍不给出答案，最终超时。请给出你的排查思路和修复方案。

::: details 参考答案

**第一步：拿到完整轨迹再说话。** 调出该会话的完整执行轨迹（每轮的模型输出、工具调用参数、工具返回、上下文快照）。没有轨迹日志就先补可观测——这是排查一切 Agent 问题的前提。

**第二步：按高频根因逐一核对。**

| 常见根因 | 轨迹上的特征 | 修复 |
|---------|-------------|------|
| 工具返回错误文本被当成正常观察 | 每轮返回都是同一段异常信息，模型换个参数继续试 | 工具返回结构化错误 + 建议动作；错误连续 N 次直接终止该工具 |
| 检索结果不含所需信息 | 返回内容正常但与问题无关，模型不断改写 query | 优化知识库覆盖/检索召回；让 Agent 在 2~3 次无效检索后改为"承认查不到并转人工" |
| 缺少循环护栏 | 参数几乎相同的调用重复出现 | 加 max_iterations、相同（工具,参数）调用去重拦截 |
| 上下文被截断，模型"忘了"已经调过 | 轨迹很长，早期调用记录已滑出窗口 | 压缩历史观察（保留摘要）、把"已尝试过的 query 列表"显式维护在上下文中 |
| 终止条件没写清楚 | 模型一直觉得"信息还不够" | 系统提示中明确给出可接受的回答标准和放弃条件 |

**第三步：分层加固（防复发）。**

1. **框架层**：递归/步数上限（如 LangGraph 的 `recursion_limit`）、单会话 token 预算与超时；
2. **工具层**：错误结构化、连续失败熔断；
3. **提示层**：显式终止条件与"无法完成时的标准动作"（道歉+转人工）；
4. **监控层**：把"单会话工具调用次数""重复调用率"做成告警指标，回归集加入本案例。

**答题关键**：先轨迹后假设、按根因分类而不是罗列技巧、修复分层落位（框架/工具/提示/监控），并把案例沉淀进回归评测。

:::

## 追问链

::: details 追问 1：如果轨迹显示每次检索的 query 都不一样、看起来都很合理，但就是查不到，你怎么判断是知识库问题还是 Agent 问题？

把 Agent 从环路中摘出来做**离线归因**：拿这批 query 直接打检索接口，人工判断"知识库里到底有没有答案"。有答案但召回不到 → 检索问题（embedding、分块、索引）；根本没有对应文档 → 内容覆盖问题；有答案且能召回但 Agent 仍不停 → Agent 的观察理解或终止判断问题。核心思路：**分层定位，别在端到端黑盒里猜**。

:::

::: details 追问 2：max_iterations 设多少合适？设小了会不会误伤复杂任务？

没有普适数值，用**数据定**：统计线上成功会话的工具调用次数分布，取 P95~P99 作为上限（客服场景通常个位数）。误伤问题用两层结构解决：触顶后不是硬失败，而是触发"降级动作"——总结当前进展、给出部分答案或转人工；对确实复杂的任务类型（如深度调研）按任务类型配置不同预算，而不是全局一刀切。

:::

::: details 追问 3：这个问题在多 Agent 系统里会更严重吗？

会，而且形态更隐蔽：子 Agent 之间可能互相委托形成**跨 Agent 环路**（A 让 B 查，B 又转回 A），单 Agent 的步数上限拦不住。需要全局层面的护栏：调用链深度上限、全局 token 预算、编排器（supervisor）对任务委托关系做环路检测，以及把"整条调用链"作为一个 trace 统一观测（trace id 贯穿所有子 Agent）。

:::
