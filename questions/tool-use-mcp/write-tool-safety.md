# 带副作用的写操作工具应该怎么设计才安全？

<QuestionMeta />

## 题目

Agent 可以调用发邮件、下单、改配置这类有真实副作用的工具。请从工具设计角度说明如何把风险控制住。

::: details 参考答案

原则：**假设模型一定会在某个时刻用错误参数调用这个工具**，安全性必须由工具层和架构层保证，而不是指望提示词。

**1. 幂等性（防重复执行）**
写请求携带幂等键，服务端同键去重；返回明确执行凭证（订单号、消息 ID）。模型不确定是否成功时的正确动作是"查询而非重试"，这条既写进工具描述，也在工具层硬保证。

**2. 可逆性设计（降低错误代价）**
优先"草稿-确认"两段式：`draft_email` 生成草稿 → 人或独立校验确认 → `send_email` 发送；删除做软删除；配置变更先落 staging。把不可逆动作改造成可拦截、可撤销的动作，比拦截模型犯错本身更可靠。

**3. 影响面限制（爆炸半径）**
单次调用的量级上限（一次最多给 1 个收件人发信、批量操作强制分页确认）；速率限制（每会话写操作次数上限）；范围白名单（只能操作当前会话绑定的租户/用户的资源）。

**4. 分级确认（human-in-the-loop）**
按（不可逆性 × 影响面）给写工具定风险级：低风险直接执行，中风险要求模型给出理由并记录审计日志，高风险强制人工确认后才执行。确认状态由执行器管理，不依赖模型"记得要确认"。

**5. 审计与可观测**
所有写调用记录完整审计日志（谁的会话、什么参数、什么依据），事故后能回放归因。

**答题关键**：幂等、可逆、限半径、分级确认、可审计——五件套；核心心态是"防御在工具层，不在提示层"。

:::

## 追问链

::: details 追问 1：草稿-确认两段式会不会让 Agent 体验变得很啰嗦？怎么平衡？

分级而不是一刀切：给用户自己发提醒邮件不需要确认，代表公司给客户发函必须确认。另外确认的形态可以轻量化——批量操作只确认一次摘要（"将给 23 人发送以下内容"）而不是逐条确认；对信任度建立后的场景提供"本类操作以后免确认"的用户授权。啰嗦的根源通常是风险分级做得太粗。

:::

::: details 追问 2：Agent 被提示注入诱导去调用写工具，上面哪些机制能兜住？

提示注入攻破的是模型的判断，所以凡是依赖模型判断的防线（提示词约束、模型自查）都可能失守，兜底靠模型外的机制：范围白名单让注入者无法操作它人资源；高风险动作的人工确认让注入的动作暴露在人眼前；速率与量级限制压缩单次攻击收益；审计日志保证事后可追溯。这正是"权限决策必须在模型外部"原则的体现。

:::

::: details 追问 3：怎么测试写工具的安全设计？

三类测试：**功能性**——幂等键重放、部分失败恢复、确认流的状态机覆盖；**对抗性**——红队构造注入提示诱导越权调用，验证白名单和确认层是否兜住；**混沌性**——写到一半超时/崩溃后的状态一致性（不能留半态）。写工具的测试标准应该向支付系统看齐，而不是向普通 API 看齐。

:::
