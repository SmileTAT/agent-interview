# 工具的 Schema 和描述应该怎么写？有哪些最佳实践？

<QuestionMeta />

## 题目

同样的后端能力，工具定义写得好坏会显著影响 Agent 的调用准确率。请给出工具 Schema 与描述的设计最佳实践。

::: details 参考答案

核心心法：**工具描述是写给模型看的 API 文档，模型只能靠它决定"何时用、怎么用"**——把它当提示词工程来做。

**描述（description）**：

1. 说清三件事：这个工具做什么、**什么时候该用**（以及什么时候不该用，尤其与相似工具的分界）、返回什么；
2. 写出关键约束与副作用："此操作不可逆""结果分页，每页最多 50 条""只覆盖 2024 年后的数据"；
3. 给一两个典型调用示例，对易错参数尤其有效。

**参数 Schema**：

1. 参数名语义化（`departure_date` 而非 `d1`），格式约束显式（"ISO 8601 日期，如 2026-07-13"）；
2. 能用枚举就不用自由字符串——把模型的猜测空间压成选择题；
3. 参数尽量少而正交：可选参数给默认值并说明默认行为；两个参数互斥/联动这类"隐藏协议"是调用错误重灾区，尽量在 schema 层面消除；
4. 复杂嵌套结构尽量拍平，深层嵌套 JSON 的生成错误率明显更高。

**验证与反馈闭环**：服务端严格校验入参，校验失败返回**具体到字段的错误信息**（"departure_date 格式应为 YYYY-MM-DD，收到 '7月13日'"），让模型能一次修正。

**迭代方法**：工具描述不是写完就完——从轨迹日志里挖调用错误的模式（选错工具、参数格式错），针对性改描述，这是提升 Agent 表现最便宜的手段之一。

**答题关键**："描述即提示词"的意识 + 枚举收窄空间 + 错误信息可指导修正 + 数据驱动迭代。

:::

## 追问链

::: details 追问 1：两个工具功能相近（比如 search_orders 和 get_order_detail），模型老是选错，怎么办？

三层递进：先在两个工具的描述里**互相划界**（"仅当已知订单号时使用 get_order_detail；按条件筛选用 search_orders"）；仍混淆则考虑**合并**为一个工具用参数区分（模型选工具比填参数更容易错）；或者反过来看是不是拆得太细——工具边界应该对齐"模型的决策粒度"而不是后端 API 的粒度。改完用历史失败 case 回归验证。

:::

::: details 追问 2：工具返回大对象（比如完整订单 JSON 有 200 个字段），该原样返回吗？

不该。按"模型需要什么"裁剪：默认返回任务相关的核心字段，提供 `fields` 参数或 detail 级别让模型按需取全量。200 个字段的返回不仅烧 token，还会稀释注意力导致后续推理变差。另一个技巧是返回中带一行摘要（"该订单共 3 件商品，状态为已发货"），模型经常只需要摘要就能决策。

:::

::: details 追问 3：怎么系统性地评测工具定义的质量？

构建"工具选择评测集"：给定一批用户请求，标注期望的（工具，关键参数）组合，跑模型统计选择准确率和参数正确率；错误按类型聚类（选错工具/漏参/格式错）定位到具体工具的描述问题。上线后监控每个工具的调用失败率与被误用率，异常的工具优先重写描述。把工具定义当代码管理：进版本库、改动跑回归。

:::
