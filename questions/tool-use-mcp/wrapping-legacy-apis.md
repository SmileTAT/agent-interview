# 如何把企业遗留系统的 API 封装成好用的 Agent 工具层？

<QuestionMeta />

## 题目

公司要给内部 ERP（上百个陈旧 SOAP/REST 接口、命名混乱、文档过时）接入 Agent。直接把 API 批量转成工具后，Agent 表现很差。你会怎么重新设计这个工具层？

::: details 参考答案

"API 批量透传"是这类项目最常见的失败模式。问题不在模型，在于**遗留 API 是为程序员设计的，不是为模型设计的**。重构思路：

**1. 从任务出发反推工具，而不是从 API 出发**
先梳理 Agent 要支持的 Top 任务（查库存、开工单、对账），每个任务设计一个语义清晰的工具，内部再去编排那些混乱的 API。上百个接口最终可能收敛为 15~20 个任务级工具。

**2. 做"翻译层"，隔离遗留系统的混乱**

- 命名翻译：`qryStkByWhs` → `query_inventory`，参数 `flg1` → 语义化枚举；
- 返回裁剪：把 300 字段的 SOAP 响应裁成模型需要的十几个字段 + 一行摘要；
- 错误翻译：把 `ERR-4032` 之类的内部错误码映射为结构化的、可指导下一步的错误信息；
- 认证/会话/重试等管道逻辑全部在封装层解决，对模型透明。

**3. 用 MCP Server 承载封装层**
把翻译层实现为 MCP Server，好处：与具体 Agent 应用解耦（多个应用复用）、工具的增删不用改应用端、便于独立做权限与审计。

**4. 数据驱动迭代**
上线后从轨迹里挖调用错误模式，持续改描述、调粒度；把高频调用序列固化为新的高层工具。

**答题关键**：任务反推而非 API 透传、翻译层四件事（命名/裁剪/错误/管道）、封装层选型（MCP）、轨迹驱动迭代。

:::

## 追问链

::: details 追问 1：业务方坚持"API 都暴露给 Agent，让它自己组合，更灵活"，你怎么回应？

用数据回应：做一个 A/B——透传版 vs 任务级封装版在同一评测集上的完成率、平均步数、成本。透传版通常在多步编排上错误率显著更高（模型要在没有文档的接口间猜协议）。灵活性诉求用兜底层满足：保留少量原子工具或一个代码执行环境给长尾需求，但高频任务必须走封装工具。"灵活"和"可靠"不是二选一，是分层。

:::

::: details 追问 2：遗留系统文档过时，你怎么知道封装的语义是对的？

别信文档，信行为：对每个要封装的 API 先做探索性测试（各种入参组合打一遍看真实响应），必要时抓生产流量样本对照；封装层带契约测试，定期回放验证遗留接口行为没变——遗留系统"静默改行为"是这类集成最大的运维风险。语义拿不准的字段宁可不暴露给模型，也不要暴露一个可能错的解释。

:::

::: details 追问 3：遗留系统慢（单接口秒级），Agent 一个任务要串七八个接口，延迟爆炸怎么办？

封装层内优化，别指望模型：任务级工具内部并发调用无依赖的接口；对稳定数据（物料主数据、组织架构）加缓存层；把"查询+轮询"模式的接口封装为异步任务工具（提交后返回任务句柄，Agent 可先做别的再来取结果）。极端情况下为高频任务建预计算视图。这些优化正是任务级封装的红利——透传架构下没有优化的抓手。

:::
