# 工具粒度怎么设计：细粒度原子工具还是高层复合工具？

<QuestionMeta />

## 题目

给 Agent 提供 20 个原子 API 工具，还是封装成 3 个高层任务工具？请分析两种取向的利弊和选择方法。

::: details 参考答案

**细粒度原子工具**（每个 API 一个工具）：

- ✅ 组合灵活，能覆盖长尾任务；单工具语义简单，模型不易用错单个工具；
- ❌ 完成一个业务动作需要多步编排，步数多 → 慢、贵、每步都是出错机会；工具数量膨胀撑上下文。

**高层复合工具**（一个工具完成一个业务任务，如 `process_refund` 内部封装查单→校验→退款）：

- ✅ 一次调用完成任务，快且稳定；业务规则（校验顺序、风控）固化在代码里而不是指望模型每次都编排对；
- ❌ 灵活性差，超出预设流程就没辙；工具本身逻辑复杂，语义变宽后模型判断"何时该用"反而更难。

**选择方法——按任务分布分层**：

1. **高频、流程固定的业务动作 → 高层工具**：这些本质是 Workflow，不该让模型每次现场编排；
2. **低频、探索性的长尾需求 → 原子工具**兜底；
3. 两层并存时在描述中明确优先级（"退款请直接使用 process_refund"）。

**第三种取向——代码执行**：当原子工具数量大（几十上百个 API）时，与其全部注册为工具，不如提供一个沙箱代码执行环境 + API SDK 文档，让模型**写代码来组合调用**。循环、过滤、聚合在代码里完成，中间数据不占对话上下文，表达力远超工具编排。代价是需要沙箱安全设施。

**答题关键**：粒度对齐"模型的决策粒度"而非后端 API 粒度；高频固化、长尾灵活；知道代码执行这个第三选项。

:::

## 追问链

::: details 追问 1：高层工具内部某一步失败了（比如退款时风控拦截），怎么让模型正确处理？

高层工具的错误返回要**暴露内部阶段**：返回"失败于风控校验，原因 X，建议动作 Y"而不是笼统的"退款失败"。这样模型能区分"该重试""该换路径""该转人工"。设计高层工具时就要枚举内部各阶段的失败模式并映射为结构化错误码——这其实是把 Workflow 的异常分支设计前置到工具层。

:::

::: details 追问 2：代码执行方案里，模型写的代码调用 API 出错和工具调用出错，处理上有什么不同？

代码执行把"多步编排错误"变成了"程序错误"，反馈质量反而更好：异常带堆栈、能精确到行，模型修代码的能力很强（有大量训练分布支撑）。工程要点：沙箱要把 API 错误如实抛给代码层而不是吞掉；限制单次执行时长与资源；对写操作 API 在 SDK 层内置幂等与确认机制，因为代码里的循环可能放大副作用（一个 for 循环发 1000 封邮件）。

:::

::: details 追问 3：工具粒度定错了怎么发现？有什么信号？

轨迹数据里的信号很明显：**粒度太细**——高频出现固定的工具调用序列模式（每次退款都是同样 4 连调），这个序列就该固化成高层工具；**粒度太粗**——模型频繁"半途放弃"高层工具改用原子工具拼装，或高层工具的参数越加越多变成"万能开关"。定期对轨迹做序列模式挖掘，是工具集演进最好的依据。

:::
