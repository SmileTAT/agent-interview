# 并行工具调用什么时候该用？有哪些坑？

<QuestionMeta />

## 题目

主流模型 API 都支持一轮输出多个工具调用并行执行。什么场景该用、什么场景危险？工程上要注意什么？

::: details 参考答案

**适用场景——无依赖的读操作**：

- 多源信息聚合：同时查天气、航班、酒店；对多个知识库并发检索；
- 批量同构查询：对 10 个订单号并行查状态；
- 收益直接：延迟从串行叠加变成取最大值，一轮模型推理替代多轮循环，token 也省（不用每次调用都重复上下文）。

**危险场景**：

1. **有依赖的调用被误并行**：模型把"先查汇率再换算下单"并行发出，第二个调用拿不到第一个的结果只能猜参数——这是并行调用最常见的事故源；
2. **写操作并行**：多个写之间的顺序、事务边界模型无法保证，并行写应默认禁止或强制串行执行；
3. **部分失败的语义混乱**：5 个并行调用 3 成 2 败，模型要能理解混合结果并只补救失败部分，而不是全部重来。

**工程要点**：

- 执行器真正并发执行（asyncio/线程池），别拿到并行请求却串行跑——那只省了推理轮次没省时间；
- 结果回填时保持调用与结果的明确对应（按 tool_call_id 配对）；
- 通过工具元数据声明"只读/有副作用"，执行器对副作用工具强制串行；
- 并发上限与限流：模型一轮发 50 个调用可能打挂下游，执行器要有并发窗口。

**答题关键**：并行是延迟优化利器但只属于无依赖读操作；依赖误判和并行写是两大坑；执行器层要有副作用感知和并发控制。

:::

## 追问链

::: details 追问 1：模型总是不并行（明明可以并发查询却一次查一个），怎么优化？

提示层明确鼓励："当多个查询互不依赖时，在同一轮中一次性发出所有调用"；few-shot 里给并行示例。也检查工具设计——如果工具本身支持批量参数（ids 数组），批量比并行更优，直接改造工具。评测上把"该并行时的并行率"做成指标跟踪，作为延迟优化的抓手。

:::

::: details 追问 2：怎么防止模型把有依赖的调用误并行？

四层防御：提示中说明"后一个调用需要前一个结果时必须分轮"；工具描述里显式写参数来源（"order_id 必须来自 search_orders 的返回"）；执行器做依赖启发式检测——参数值是占位符模式（"<上一步结果>"之类）直接拒绝并回传错误让模型分轮重发；对强依赖链路干脆合并成一个复合工具，从根上消除编排空间。

:::

::: details 追问 3：并行调用的部分失败，重试策略和串行有什么不同？

关键是**只重试失败子集**且保留成功结果：执行器把成功结果正常回填，失败的回填结构化错误，让模型下一轮针对性补救。要避免两个极端——整批重跑（浪费且对副作用工具危险）和静默丢弃失败（结果不完整还不自知）。对幂等的读操作，执行器甚至可以在框架层先自动重试一次，减少一轮模型往返。

:::
