# Agent 的权限最小化怎么落地？凭证应该怎么管理？

<QuestionMeta />

## 题目

"给 Agent 一个管理员 token 先跑起来"是常见的起步方式，也是事故温床。请说明 Agent 权限体系的设计原则与凭证管理实践。

::: details 参考答案

**原则：Agent 的权限 = f(代表谁, 干什么任务)，而不是一份静态的全能凭证。**

**1. 身份模型——Agent 以"代理身份"行动**
Agent 访问资源时应携带**用户的身份与权限**（on-behalf-of 模式），而不是一个高权限服务账号：用户 A 的会话里，Agent 天然只能查到 A 有权看的数据——大量越权问题在身份层直接消解。服务账号只用于 Agent 自身的基础设施操作，且独立最小授权。

**2. 任务级收窄**
在用户权限的基础上，再按当前任务裁剪：查询类任务不给写权限、本次任务只涉及项目 X 就不给项目 Y 的访问。实现上用**短时效、窄范围的派生凭证**（scoped token）：任务开始时按需签发、任务结束即失效。

**3. 凭证不过模型上下文（铁律）**
API key、token 绝不能出现在提示或对话历史里——上下文会被日志记录、可能被注入攻击诱导复述。正确做法：模型只产生"调用意图"（工具名+业务参数），**凭证由执行器在模型外部注入**请求。MCP 架构里凭证由 Server 端持有，天然符合这条。

**4. 工具即权限边界**
不给"通用 SQL 执行"这种开放工具，给"查询本租户订单"这种预置了范围约束的工具——把权限语义编译进工具实现，模型再怎么被诱导，参数空间里也表达不出越权操作。

**5. 审计与再认证**
所有资源访问以"用户+Agent+任务"三元组记录；敏感操作触发用户再确认（权限存在≠此刻该用）。

**答题关键**：代理身份模型、任务级派生凭证、凭证不进上下文、用工具设计固化权限边界。

:::

## 追问链

::: details 追问 1：on-behalf-of 模式在技术上怎么实现？下游系统不支持怎么办？

标准路径是 OAuth 的委托授权（token exchange / OBO flow）：用户登录态换取面向下游资源的、带用户身份的访问令牌，Agent 执行器持有并按需使用。下游是遗留系统不支持 OAuth 时，在封装层（如 MCP Server）做**应用层代理鉴权**：Server 用服务账号连底层系统，但每次调用前按传入的用户身份在自己这层做权限校验+行级过滤——权限逻辑上移到封装层。这不如原生 OBO 干净（封装层成为高价值攻击目标，要重点加固），但是现实中最常见的过渡方案。

:::

::: details 追问 2：Agent 需要的权限事先不可知（探索性任务），最小化和可用性怎么平衡？

用**渐进授权**代替预先全授权：起步只给只读基础权限，任务中确需更高权限时，Agent 发起权限请求（说明用途），由用户/策略引擎即时批准并签发窄范围短时凭证——把"要权限"变成一个显式的、可审计的交互，而不是预先塞满。配合权限使用分析：定期统计各类任务实际用到的权限集，收敛默认授权模板。体验上类似手机 App 的运行时权限模型。

:::

::: details 追问 3：多 Agent 系统里权限怎么传递？子 Agent 继承主 Agent 的全部权限吗？

不应全量继承——委托时做**权限衰减**：子 Agent 拿到的凭证范围 ≤ 主 Agent ∩ 子任务所需（衰减委托）。工程上主 Agent 委托任务时同时申请一张更窄的派生凭证给子 Agent；调用链身份要完整传递（audit 时能看到"用户→主 Agent→子 Agentn"的链路）。要防的经典漏洞是"混淆代理人"（confused deputy）：低权限请求者诱导高权限 Agent 替它干越权的事——每一跳都按原始请求者的权限校验，而不是按直接调用者。

:::
