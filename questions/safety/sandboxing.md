# 为什么 Agent 执行代码必须用沙箱？沙箱要隔离什么？

<QuestionMeta />

## 题目

代码执行是 Agent 最强大的工具，也是最大的攻击面。请说明沙箱的必要性、要隔离的维度和常见实现层次。

::: details 参考答案

**为什么必须沙箱**：Agent 执行的代码有两类来源风险——模型自己写错（无意的 `rm -rf`、失控循环），以及**被注入操纵后故意写坏**（间接注入让 Agent"顺手"写出外传数据的代码）。代码执行让注入攻击从"说错话"升级为"任意代码执行"，所以代码执行环境必须按"运行不可信代码"的标准建设，无论代码看起来多无辜。

**要隔离的四个维度**：

1. **文件系统**：只挂载任务需要的目录（工作目录可写、其余只读或不可见）；宿主机的凭证文件（`~/.ssh`、云凭证、浏览器数据）绝不可见——这是数据外泄的头号目标；
2. **网络**：默认拒绝出站，按白名单放行（包管理源、任务明确需要的 API）；无限制出站 = 注入攻击的外传通道 + 沦为攻击跳板的风险；
3. **资源**：CPU/内存/磁盘/进程数/执行时长的硬限额，防失控代码耗尽宿主（挖矿、fork 炸弹、死循环）；
4. **权限与内核面**：非 root 运行、削减能力（capabilities）、限制系统调用面（seccomp 等），防提权逃逸。

**实现层次（隔离强度递增）**：进程级限制（最弱，仅防误伤）→ 容器（namespace/cgroup，主流起点，但共享内核，逃逸并非不可能）→ 用户态内核/轻量虚拟机（gVisor / Firecracker 类 microVM，云厂商代码执行服务的标准形态）→ 独立虚拟机/物理隔离（最强，多租户场景的稳妥选择）。选型按"谁的代码在跑"定：只跑自家 Agent 的低敏任务，容器+严格网络策略可接受；多租户平台必须 microVM 级。

**运维配套**：环境用完即毁（不留状态）、镜像最小化（少装工具=少攻击面）、执行全量审计（代码、输出、网络行为）。

**答题关键**："按不可信代码对待"的心态 + 四维隔离（文件/网络/资源/内核面）+ 分层实现与选型依据。

:::

## 追问链

::: details 追问 1：沙箱里的代码需要访问内部数据（比如分析数据库数据）才能完成任务，怎么给数据又不破坏隔离？

数据进沙箱，凭证不进：在沙箱**外**用受控通道把所需数据快照/子集注入沙箱工作目录（或提供一个网关型数据 API，白名单放行、网关侧做鉴权与行级过滤），沙箱内代码只见数据不见凭证。反模式是把数据库连接串给沙箱直连——等于把凭证送进不可信环境。输出同理：结果文件通过受控通道取出并校验，不让沙箱直接写外部系统。

:::

::: details 追问 2：网络默认拒绝会废掉很多能力（pip 装包、调 API），白名单怎么管才不至于形同虚设？

分层放行：**包管理源**走内部镜像代理（可审计、可缓存、可挡恶意包）；**任务 API**按任务类型预声明域名白名单，而不是运行时任意加；剩余一律拒绝并记录被拒请求——**被拒日志是注入攻击的重要探测器**（沙箱里的代码试图访问陌生域名，本身就是强告警信号）。警惕"白名单放了个通配 CDN/对象存储域名"这种事实上的任意外传通道，放行粒度要到具体前缀。

:::

::: details 追问 3：浏览器自动化 Agent（操作真实网页）怎么沙箱？它天然要访问全网。

浏览器场景隔离目标变了：不是限制出站，而是**限制"这个浏览器会话能代表谁"**。要点：浏览器跑在隔离环境里，不复用用户日常浏览器的登录态/Cookie（否则网页注入可以直接以用户身份行动）；需要登录的站点用专用的受限账号或即时授权；下载的文件落沙箱按不可信文件处理；高危动作（支付、发布）过 HITL。同时网页内容是典型的不可信输入，注入防御（内容与决策分离）在这里最重要——浏览器 Agent 是"三要素齐全"的高危形态。

:::
