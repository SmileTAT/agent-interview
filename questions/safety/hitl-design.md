# Human-in-the-loop 应该怎么设计？哪些操作需要人工确认？

<QuestionMeta />

## 题目

人工确认是 Agent 安全的最后闸门，但设计不好会沦为"点点点疲劳"。请说明 HITL 的分级标准、交互设计与工程实现。

::: details 参考答案

**哪些操作需要确认——二维分级**：风险 =（不可逆性）×（影响面）。

| | 影响面小 | 影响面大 |
|---|---------|---------|
| **可逆** | 自动执行 | 自动执行 + 事后通知 |
| **不可逆** | 确认（轻量） | 强制确认 + 理由展示 |

外加两个独立触发器：**对外可见的动作**（代表组织发出的邮件/评论，错误代价含声誉）和**模型自报不确定**（置信度低时主动升级）无论象限都应确认。

**交互设计——确认的质量决定这道闸门是否真的存在**：

1. **给足决策信息**：确认界面要展示"做什么、对谁、依据是什么、如何撤销"，而不是一句"是否继续？"——信息不足的确认只会训练用户无脑点是；
2. **默认值保守**：超时不响应 = 拒绝，而不是放行；
3. **批量聚合**：批量操作确认一次摘要（"将归档 37 封邮件，列表如下"），不逐条轰炸；
4. **对抗确认疲劳**：确认频率是核心健康指标——确认太频繁说明分级门槛错了，用户开始盲点"是"时这道防线已经失效。给用户"本类操作以后免确认"的显式授权通道，把节省下来的注意力留给真正的高危确认。

**工程实现**：确认状态由**执行器/编排层**管理（不依赖模型"记得要问"）——工具元数据声明风险级，执行器拦截高危调用、挂起任务、持久化状态（checkpoint），等待人工决议后恢复执行。长时挂起要可持久化（人可能几小时后才批），这正是 LangGraph 等框架 interrupt + checkpoint 机制的典型用途。审批记录全量入审计日志。

**答题关键**：二维分级 + 确认界面的信息质量 + 确认疲劳是失效信号 + 拦截在执行器层而非提示层。

:::

## 追问链

::: details 追问 1：用户授权了"以后免确认"，出事算谁的？这个授权机制怎么设计才稳妥？

授权要有边界和留痕：授权按**操作类别+范围**（"允许自动归档邮件"而非"允许一切"）、可随时撤销、有有效期；授权后该类操作仍然全量审计+事后可见（活动摘要），用户随时能发现异常并收回。出事责任上，产品要保证"授权时用户理解了范围"（清晰的授权文案）——法务层面这是知情同意问题。技术上即使免确认，速率与量级护栏仍然生效：免确认≠无限制。

:::

::: details 追问 2：7×24 运行的自主 Agent，半夜触发高危确认没人在，怎么办？

按业务分三种策略：**可等待的**——挂起到有人处理（checkpoint 持久化，任务不丢）；**时效敏感的**——降级到安全的保守动作（如告警场景先执行只读缓解措施+通知 on-call，破坏性修复等人批）；**预授权剧本**——对可预见的紧急场景，提前由人审定标准处置剧本，Agent 半夜按剧本执行并留痕。核心思想：无人值守时段收窄自主边界，而不是取消闸门。

:::

::: details 追问 3：怎么评估 HITL 机制的有效性？

四个指标：**拦截价值**——确认环节的拒绝率（从不拒绝说明门槛过严或界面无效）；**确认疲劳**——人均确认次数/天、平均响应时长、"秒批率"（响应快到不可能看过内容的比例，盲点行为的直接信号）；**漏网率**——事后审计发现的"该确认而未确认"的高危操作数；**效率代价**——确认导致的任务时延。健康形态是：确认次数少、每次都有信息量、拒绝率不为零、漏网率为零。

:::
