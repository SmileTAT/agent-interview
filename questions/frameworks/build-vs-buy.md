# 要不要自研 Agent 框架？自研和开源框架怎么权衡？

<QuestionMeta />

## 题目

团队规模中等、有多个 Agent 业务线。架构评审上有人主张自研统一框架，有人主张全面拥抱开源框架。请给出你的分析框架和建议。

::: details 参考答案

**先校准一个事实：Agent"框架"的核心并不厚。** Agent 循环本身（模型调用+工具分发+循环控制）几百行可以写清楚；真正有分量的是周边工程——持久化、可观测、评测、HITL、部署运维。所以问题不是"能不能自研"，而是**哪些层值得自己拥有**。

**分层决策而不是整体二选一**：

| 层 | 建议 | 理由 |
|---|------|------|
| 模型接入层 | 薄自研封装 | 隔离供应商差异，掌握完整请求可见性，量小价值大 |
| Agent 循环/编排 | 视复杂度：简单自研，复杂用开源（LangGraph 类） | 循环简单时框架是负资产；复杂控制流+checkpoint 自研成本高 |
| 工具层 | 标准协议（MCP） | 生态红利，天然解耦 |
| 可观测/评测 | 优先开源标准（OTel）+ 自建评测集 | 评测集是核心资产必须自有，采集协议没必要自造 |
| 业务 Agent 本身 | 自研 | 这是你的产品，没有替代 |

**倾向自研的信号**：需求非常规（框架的抽象天天要绕）、性能/成本敏感（要压缓存命中和上下文的极致控制）、合规要求全链路自主可控、团队有长期维护承诺。

**倾向开源的信号**：需求在框架能力主航道内、团队小或流动大（自研框架变孤儿的风险）、需要快速验证业务。

**最该避免的两个坑**：为"技术统一"而自研一个内部框架强推所有业务线（内部框架的文档与维护通常远差于开源，统一收益是幻觉）；以及全盘依赖厚框架后失去对模型交互层的可见性。

**答题关键**：分层决策代替二选一、"评测集与业务 Agent 才是核心资产"、说得出自研的维护成本。

:::

## 追问链

::: details 追问 1：如果选择自研核心循环，最容易低估的工作量是什么？

不是循环本身，是长尾工程：流式+工具调用+错误重试的组合状态机（各家 API 的流式事件语义差异）、上下文窗口管理与压缩、并发下的限流与配额调度、checkpoint 与幂等恢复、以及**跟着供应商 API 演进持续维护**（新的工具类型、新的消息格式，每季度都有）。评估自研时把这些列进预算——很多"两周写个框架"的项目死在第 90 天的维护上。

:::

::: details 追问 2：多个业务线用不同框架，平台团队怎么治理？强制统一吗？

不强制框架，**统一契约**：约定所有 Agent 必须满足的横切标准——trace 格式（OTel）、评测接入方式、工具接入协议（MCP）、部署打包规范、安全基线（凭证管理、审计）。框架是业务线的实现细节，契约是平台的治理抓手。这比强推统一框架现实得多：迁移成本为零的统一才推得动，而契约层的统一恰好覆盖了平台真正关心的东西（可观测、可评测、可审计、可运维）。

:::

::: details 追问 3：一年后开源框架大版本重写/停止维护了怎么办？这个风险怎么提前对冲？

本领域框架半衰期确实短，对冲手段：**依赖面收窄**——业务代码只通过自己的薄适配层用框架，禁止框架类型渗透进业务逻辑（换框架=重写适配层）；**资产框架无关化**——提示、工具、评测集独立存放；**版本锁定+跟进节奏自主**——不追每个新版本，按季度评估升级；选型时看框架的治理信号（背后组织、release 节奏、breaking change 记录）。把"框架被弃"当作确定会发生的事来设计，发生时就只是个工程任务而不是灾难。

:::
