# LangGraph、AutoGen、CrewAI、各家 Agent SDK 怎么选型？

<QuestionMeta />

## 题目

主流 Agent 框架各有取向。请给出选型框架（judging criteria），并说明各家的定位差异。

::: details 参考答案

**先立判据再看产品**，五个维度：控制流表达力、状态与持久化、可观测与调试、生产成熟度（部署/扩缩/HITL 支持）、抽象的"厚度"（封装了多少，出问题时能不能下钻）。

**各家定位（以 2025-2026 的生态为准）**：

- **LangGraph**：把 Agent 建模为**显式状态图**——节点/边/共享状态，原生 checkpoint 持久化、interrupt（HITL）、时间回溯。控制流复杂、要长时任务恢复、要精确干预的生产系统首选；代价是概念多、上手陡；
- **AutoGen（微软）**：以**多 Agent 对话**为核心抽象，Agent 间通过消息协作，适合研究性、探索性的多 Agent 实验；生产化配套相对薄，微软系后续与其企业栈整合演进较快，选型要看最新状态；
- **CrewAI**：**角色/团队**隐喻（role、task、crew），上手最快，快速原型和轻流程自动化友好；抽象较厚，深度定制或复杂控制流容易顶到天花板；
- **模型厂商 Agents SDK**（OpenAI Agents SDK、Claude Agent SDK 等）：轻量原语（agent、tool、handoff/子代理），与自家模型能力（原生工具、缓存、多模态）咬合最好，官方维护降低跟进成本；跨供应商可移植性要自己评估；
- **不用框架（直接调 API + 自己写循环）**：Agent 循环本质是"while + 工具分发"，几百行能写清楚。依赖极简、完全可控，很多团队的生产系统就是这么跑的——框架不是必需品。

**选型建议路径**：简单任务/原型 → SDK 或裸写；控制流复杂/需持久化恢复/强 HITL → LangGraph 类；强绑定某模型生态 → 该家 SDK；多 Agent 研究实验 → AutoGen。**警惕用框架的复杂度证明架构的先进性**——面试中说得清"为什么不用框架"往往比背框架特性更加分。

**答题关键**：判据先行、各家一句话定位、"裸写也是正当选项"的判断力。

:::

## 追问链

::: details 追问 1：框架的"厚抽象"具体会在什么时候坑到你？

三个典型时刻：**调试时**——错误发生在框架内部的提示拼装/重试逻辑里，你看不见它替你做了什么（比如框架自动注入的隐藏提示改变了模型行为）；**优化时**——想精确控制上下文/缓存前缀，发现框架的消息管理不透明或不可插拔；**升级时**——框架大版本重构 API（本领域框架迭代极快），业务代码被迫跟着重写。缓解：选型时验证"能不能看到最终发给模型的完整请求"，这是抽象是否失控的试金石。

:::

::: details 追问 2：团队已经用某框架重度绑定，现在想换/想解耦，怎么办？

先分离"值得保留的资产"与"框架胶水"：评测集、提示词、工具实现、业务逻辑是资产，编排代码是胶水。解耦路径：把工具实现收敛到框架无关的模块（或 MCP Server——天然的解耦层）；提示与模型调用收敛到自有的薄封装；编排层最后处理（它才是框架绑定的核心，也最薄）。实操建议增量迁移：新功能用目标架构写，旧链路维持运行，用评测集保证迁移等价性。

:::

::: details 追问 3：面试官追问"你们为什么选X而不是Y"，怎么答才不像背书？

好答案的结构是"约束→取舍→验证"：先摆自己场景的关键约束（比如"客服任务需要人工审批挂起 48 小时后恢复"→ 持久化 checkpoint 是硬需求），再说这个约束淘汰了谁、留下了谁，最后讲验证过程（拿两个候选各做了一周 spike，比较了调试体验和改造成本）。忌讳泛泛的"X 更成熟""社区更大"。说得出"我们为此放弃了什么"（如接受了学习成本）的回答，才可信。

:::
