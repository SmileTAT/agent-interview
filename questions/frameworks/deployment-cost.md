# Agent 服务的部署形态与成本优化有哪些要点？

<QuestionMeta />

## 题目

Agent 服务上线后，成本和容量问题会很快浮现。请说明 Agent 服务的部署架构要点和成本优化的主要抓手。

::: details 参考答案

**部署形态：Agent 是"长时、有状态、突发外部依赖"的工作负载**，与无状态 Web 服务的套路不同：

1. **执行层独立**：任务跑在队列+worker 池（或工作流引擎）上，与 API/连接层解耦（见流式与中断一题）；长任务（分钟~小时级）必须可 checkpoint 恢复，部署发版不杀任务；
2. **并发模型**：Agent 的瓶颈在等待外部 IO（模型 API、工具），天然适合异步/协程密集的 worker；容量规划的关键指标是**并发任务数 × 每任务的模型调用速率**，向上游 API 的配额（RPM/TPM）对齐——上游配额往往才是真正的容量上限；
3. **背压与配额调度**：面向多个业务方时要有队列优先级与租户配额，防止一个批量任务把交互式流量的模型配额抽干；对上游限流要有优雅的排队降速而不是雪崩重试。

**成本优化的抓手（按性价比排序）**：

1. **缓存命中率**：Agent 多轮循环天然适合 prompt caching，守住"稳定前缀+只追加"，命中率是第一大杠杆；
2. **模型分级路由**：按环节用不同档模型（规划用强模型、执行/抽取用小模型），配合难度路由；
3. **上下文瘦身**：工具返回裁剪、历史压缩——token 就是钱，浪费的输入 token 是纯损耗；
4. **批处理通道**：非实时任务走批量 API（通常有大幅折扣），和交互流量分池；
5. **止损机制**：单任务 token/成本预算硬上限、失控检测（异常步数告警）——一个死循环任务一晚上能烧出惊人账单；
6. **单位经济学监控**：每任务成本、每成功任务成本按业务线看板化，成本异常当事故处理。

**答题关键**：执行与连接解耦、容量对齐上游配额、缓存/路由/瘦身三大杠杆、止损与单位经济学。

:::

## 追问链

::: details 追问 1：怎么做 Agent 服务的容量规划？压测和 Web 服务有什么不同？

不同点：瓶颈不在自身 CPU 而在上游模型配额与工具下游，压测要**模拟真实任务混合**（不同任务的步数与 token 分布差异巨大）而不是打恒定 QPS；观测的核心是任务排队时长、上游限流率、端到端完成时间分位数。规划公式粗略为：可支撑并发任务 ≈ 上游 TPM 配额 ÷ 每任务平均 token 速率，再打安全余量。突发应对：优先级队列+非实时任务可延迟调度，比盲目扩 worker 有效——worker 不是瓶颈。

:::

::: details 追问 2：多供应商/多模型的路由与故障切换怎么设计？

两层：**能力路由**（按任务难度/类型选模型档位，成本优化）和**可用性路由**（供应商故障/限流时切备用），分开配置。切换要点：备用模型的行为差异会影响 Agent 质量，核心链路的备选模型要提前跑过评测集，而不是故障时裸切；会话中途切模型要注意缓存全失效与风格突变，尽量以任务为边界切换；对幂等的失败请求做跨供应商重试，非幂等的不做。配额管理集中到一个网关层，业务方无感。

:::

::: details 追问 3：老板问"能不能把 Agent 成本降一半"，你的排查与优化顺序是什么？

先测量再动手：按业务线×任务类型拆解成本，找 top 消耗源。常见发现与对应动作依次是——缓存命中率低（前缀里有动态内容，修了立竿见影）；工具返回没裁剪/历史没压缩（上下文瘦身）；全链路用顶级模型（分级路由，把抽取/格式化类步骤降档）；失败任务重跑浪费（修稳定性本身就是省钱）；批量任务挤在实时通道（迁批量 API）。经验上前两项经常就能完成大头目标，且不碰质量；动模型档位才需要评测护航。

:::
