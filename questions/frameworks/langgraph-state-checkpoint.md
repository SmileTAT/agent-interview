# LangGraph 的状态机与 checkpoint 机制解决什么问题？

<QuestionMeta />

## 题目

LangGraph 的核心卖点是"把 Agent 建模为带持久化的状态图"。请解释状态图与 checkpoint 各自解决的问题，以及典型使用模式。

::: details 参考答案

**状态图解决"控制流的可控性"**：

- 建模：应用 = 图（节点是步骤/Agent，边是转移，条件边表达分支），所有节点读写一个**共享状态对象**（typed state，如消息列表+业务字段），每步的输入输出显式声明合并方式（reducer）；
- 对比裸 while 循环的收益：控制流**可见且可约束**——哪些路径合法是图定义好的，模型的自由决策被限制在条件边的选项内；复杂流程（分支、并行节点、循环上限 recursion_limit）有一等公民的表达，而不是散落在 if/else 里。

**checkpoint 解决"长时任务的生命周期"**：

- 机制：每个超级步（superstep）后把完整状态快照持久化（内存/SQLite/Postgres 等 checkpointer），以 thread_id 组织；
- 由此获得的能力全家桶：
  1. **崩溃恢复**：进程挂了从最近 checkpoint 续跑，长任务不清零；
  2. **human-in-the-loop**：`interrupt` 在任意节点暂停、状态落盘，等人工批准（可以是 48 小时后）再 resume——审批型流程的刚需；
  3. **时间回溯与分叉**：回到历史某步的状态重放/改参重试，调试利器；
  4. **多轮会话记忆**：同 thread_id 的状态天然跨请求延续。

**典型模式**：客服升级流程（自动处理 → 高危动作 interrupt 等人批 → 恢复执行）、长程调研任务（分阶段 checkpoint，可断点续跑）、需要回溯调试的复杂编排。

**代价与判断**：状态 schema 设计、图的样板代码、checkpointer 运维都是成本。**没有"暂停等人""崩溃续跑""复杂分支"需求的简单 Agent，用不到这套重武器**——这句判断在面试中很重要。

**答题关键**：状态图=控制流可控、checkpoint=暂停/恢复/回溯三件套、说得出什么时候不需要它。

:::

## 追问链

::: details 追问 1：checkpoint 存了完整状态，长对话下存储会不会爆炸？

会线性增长（每步一个快照），治理手段：checkpointer 按 thread 设保留策略（只留最近 N 个快照 + 关键里程碑）；状态 schema 里大对象外置（文件内容放对象存储，状态里存引用）——这同时也是上下文管理的好习惯；已完结 thread 的快照降冷归档。另外注意快照里可能含敏感对话内容，存储加密与访问控制要跟上（等同于 trace 的隐私要求）。

:::

::: details 追问 2：interrupt 恢复执行时，外部世界可能已经变了（比如审批等了两天，库存变了），怎么处理？

不能盲目 resume。模式：恢复点设计成"重新校验节点"——resume 后第一步重新拉取关键外部状态并与快照对比，变化超过阈值则回到规划/确认环节而不是继续执行旧计划；审批的决议要带时效（超时作废重新发起）；写操作的前置条件在执行瞬间再查一次（乐观锁思路）。原则：checkpoint 恢复的是"我们的进度"，不是"世界的状态"，两者要显式对账。

:::

::: details 追问 3：条件边的路由是模型决定的，状态图还能算"可控"吗？

可控性体现在**决策空间的收窄**而非消灭决策：模型在条件边只能从枚举的合法转移中选（选项外的输出被拒绝/重试），而裸循环里模型理论上能"发明"任何下一步。此外图结构让不变量可强制：某节点永远先于某节点、危险节点必经审批节点、循环有 recursion_limit。可以把它理解为"给模型的自由度画了轨道"——轨道内自由，轨道本身由工程定义。这正是生产系统要的平衡点。

:::
