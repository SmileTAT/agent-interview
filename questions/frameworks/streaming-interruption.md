# Agent 的流式输出与中断恢复怎么实现？

<QuestionMeta />

## 题目

对话式 Agent 需要流式体验，长任务 Agent 需要可中断可恢复。请说明这两块的工程实现要点。

::: details 参考答案

**流式的特殊性：Agent 的流不是一条纯文本流**，而是多类型事件的交错序列——文本增量、思考过程、工具调用开始/参数增量/执行中/结果、步骤切换、错误。实现要点：

1. **事件协议设计**：对客户端定义结构化事件流（SSE/WebSocket），事件带类型与步骤归属，前端才能渲染"正在搜索资料…"这样的过程反馈——Agent 产品的体验差异很大程度在过程可见性；
2. **多级转发**：模型 API 的流式事件 → 服务端聚合/过滤（如思考内容按策略摘要或隐藏）→ 转发给客户端；工具执行期间没有模型流，要主动发心跳/进度事件填补"静默期"；
3. **流式与工具调用的衔接**：工具参数是增量到达的，须等一个调用的参数完整（事件边界）才能执行；一轮多个并行调用要正确聚合。

**中断恢复的两类场景**：

- **用户主动中断**（"停一下/改个方向"）：循环在每步边界检查取消信号；正在执行的写操作要安全收尾（完成或回滚，不留半态）；中断后保留已完成的轨迹与部分产出，用户修正后**从中断点带着已有进展继续**，而不是从头再来——这依赖状态持久化（checkpoint）；
- **被动中断**（连接断开、服务重启、部署）：会话状态与执行进度持久化在服务端（不依赖连接存活）；客户端重连后按最后确认的事件序号**续传事件流**（事件带单调序号，服务端保留近期事件缓冲）；执行侧从 checkpoint 恢复，配合工具幂等避免重复副作用。

**架构含义**：这要求"执行"与"连接"解耦——Agent 任务跑在独立的执行层（任务队列/工作流引擎），连接层只是事件的订阅通道。把执行绑在 HTTP 请求生命周期里的 Agent，永远做不好中断恢复。

**答题关键**：事件流而非文本流、静默期填补、两类中断的差异、执行与连接解耦这个架构结论。

:::

## 追问链

::: details 追问 1：用户中断时模型正在生成一半，这半截输出怎么处理？

分类处理：**半截文本回答**——保留展示并标注"已中断"，它可能已有价值；**半截工具调用**——参数不完整，直接丢弃不执行（绝不能补全执行）；**已发出未返回的工具执行**——读操作等它完成或放弃皆可，写操作必须等到确定态（成功/失败/回滚），不能在"不知道执行没执行"的状态下继续。恢复对话时，把"上次中断于何处、哪些已完成"作为上下文告知模型，避免它重复或凭空承接。

:::

::: details 追问 2：事件续传的缓冲区设计：保留多少？错过了怎么办？

按会话保留一个有限的近期事件环形缓冲（比如最近几百条或几分钟），重连时从客户端报的序号续发；超出缓冲范围就不逐条补了——发一个**状态快照事件**（当前完整状态：已完成步骤摘要+最新输出），客户端全量刷新后继续增量。这借鉴了流式系统"快照+增量"的经典模式。要避免的是无限缓冲（内存炸）和断连即丢（体验差）两个极端。

:::

::: details 追问 3：移动端弱网环境，这套架构还需要加什么？

三点强化：**推拉结合**——长连接不可靠，客户端支持降级为轮询拉取状态快照；**任务托管心智**——UI 上把长任务表现为"已提交，可离开"，完成后推送通知召回用户，而不是要求保持在线盯着流；**幂等的用户操作**——弱网下用户会重复点击（重试发送、重复中断），请求带客户端生成的操作 ID 去重。本质上把"实时流式对话"降级预案设计成"异步任务+通知"，两种模式共用同一个执行层。

:::
