# Agent 的线上 A/B 测试和灰度发布有哪些特殊注意点？

<QuestionMeta />

## 题目

离线评测通过后，Agent 的改动要上线验证。相比传统功能的 A/B，Agent 的线上实验有什么特殊性？请给出实践方案。

::: details 参考答案

**特殊性一：指标是"任务级"的，且反馈滞后**
Agent 的核心指标（任务解决率、无需人工兜底率）以任务/会话为单位，一次会话跨多轮甚至多天；"是否真解决"可能要等 24h 内无重开才能确认。设计上：**随机化单元用用户而不是请求**（同一用户在一次任务中必须命中同一版本，否则体验割裂且数据污染）；指标计算窗口要覆盖反馈滞后期。

**特殊性二：方差大，功效不足是常态**
Agent 行为随机性 + 任务难度分布不均，指标噪音远大于点击率类实验。对策：按任务类型分层随机化与分层分析；用 CUPED 类方差缩减；实验周期宁长勿短；小流量灰度阶段只看**护栏指标**（错误率、越权操作、延迟、成本）判断"没变坏"，质量结论留给足量的正式实验。

**特殊性三：失败的代价可能是真实副作用**
新版本的 bug 不是"页面不好看"而是"发错邮件"。所以灰度必须配：分级放量（内部 → 1% → 10%...）、**新版本先跑影子模式**（shadow：新版并行生成但不执行副作用，与旧版对比决策差异）、快速回滚开关、写操作的审计告警在灰度期加严。

**特殊性四：成本也是实验指标**
新提示可能让完成率 +2% 但 token 成本 +40%。实验报告强制带单位经济学：每任务成本、每成功任务成本。

**答题关键**：用户级随机化 + 滞后与方差的应对 + 影子模式与分级放量 + 成本入指标。

:::

## 追问链

::: details 追问 1：影子模式下 Agent 有工具调用，怎么"并行但不执行"？

把工具层做成可切换的执行模式：**读操作真执行**（无副作用，且新版需要真实观察才能继续推理）；**写操作 mock**——返回模拟成功（带合成凭证），让轨迹能走完但不落真实副作用。对比分析新旧版的轨迹分歧点（第一次决策不同发生在哪步）。局限要认识到：mock 写操作后的后续轨迹是"假设性的"，只能评估决策差异，不能完全等价于真实执行——所以影子模式是灰度前的过滤器，不是替代品。

:::

::: details 追问 2：模型供应商静默升级了底层模型，你的 A/B 结论会失效吗？怎么防护？

会——你以为在比较"提示 A vs 提示 B"，其实底层模型中途换了，实验被污染。防护：生产环境**锁定模型版本号**（用带版本的模型 ID 而非 latest 别名）；记录每次请求的实际模型版本入 trace；建立"模型版本变更"的变更管理流程——供应商升级时当作一次正式发版，跑完整评测和灰度，而不是被动接受。这是 LLM 应用特有的"依赖漂移"问题，很多团队吃过闷亏。

:::

::: details 追问 3：Agent 改动很频繁（每周多次调提示），每次都跑两周 A/B 根本来不及，怎么办？

分级发布策略：把改动按风险分级——低风险（改措辞、加示例）走"离线评测 + 护栏监控"直接发，不做正式 A/B；中风险（改流程、换工具）走短周期灰度看护栏；只有高风险改动（换模型、重写核心提示、改架构）才值得完整 A/B。同时把多个小改动**攒批**做一次实验。关键基础设施是强大的离线评测集与护栏监控——它们承接了大部分验证职责，A/B 只留给真正需要因果结论的大决策。

:::
