# 从零为一个新 Agent 搭建评测体系，你会怎么做？

<QuestionMeta />

## 题目

团队刚做出一个 Agent 原型（比如内部 IT 支持 Agent），目前全靠"感觉不错"。请给出从零搭建评测体系的路线图。

::: details 参考答案

**第一步：定义"好"——先写验收标准再写用例**
和业务方对齐：什么算任务成功（问题解决且无需人工兜底？）、什么是不可接受的失败（错误操作、泄露信息）、质量之外的约束（延迟、成本上限）。没有这一步，后面全是自嗨。

**第二步：攒第一批用例（20~50 个就够起步）**
来源三路：真实用户请求采样（最重要，别自己编）、领域专家给的典型任务与边界情况、已知的失败案例。每个用例 = 输入 + 判定标准（期望结果或检查项），并覆盖三类：正常任务、边界/坏天气（工具故障、信息不全）、安全红线（越权请求应拒绝）。**小而真实 > 大而合成**。

**第三步：搭自动化跑评测的管道**
一条命令跑全集、输出分数报告与逐例 diff；判定方式按用例性质混用——可断言的用规则（调用了正确工具、包含关键信息、没碰禁止操作），开放性的用 LLM-as-Judge（带 rubric），少量关键用例保留人工评审。轨迹和结果都要存档，支持两次运行的对比。

**第四步：接入研发流程，形成闭环**
改提示/换模型/加工具必跑评测（当 CI 门禁）；上线后**坏例回流**——线上每个确认的 bad case 进评测集（这是评测集成长的主引擎）；每月审视指标与用例集的代表性。

**成熟度演进**：规则断言起步 → 加 LLM Judge 与轨迹级指标 → 线上监控与评测联动（线上指标劣化能定位到评测盲区）。

**答题关键**：先定义成功、小规模真实用例起步、自动化+混合判定、坏例回流的闭环——体现"评测是流程而不是一次性项目"。

:::

## 追问链

::: details 追问 1：业务方说"就跑 10 个例子能说明什么？"怎么回应样本量质疑？

两点回应：一，10 个真实高频用例已经能拦住最伤的回归（核心场景挂了立刻知道），这是下限保障不是统计推断；二，样本量随坏例回流自然增长，三个月后自然有几百个——重点是**先建立"改动必评测"的流程**，流程在，集子会长大；流程不在，一千个用例也是摆设。同时对完成率这类比例指标标注置信区间，明确当前样本量下能分辨多大的差异，避免过度解读小差距。

:::

::: details 追问 2：Agent 的输出每次都不一样，评测结果不稳定怎么办？

三个手段：**判定标准面向不变量**——不比对逐字输出，断言"任务效果"（工单创建成功、答案包含正确结论），措辞变化不影响判分；**多次采样**——每用例跑 3~5 次报告通过率分布，把"偶尔失败"显性化（它恰恰是重要信号）；**分离方差来源**——温度调零复跑，若仍不稳定则是提示/流程的问题而非采样问题。接受一个现实：Agent 评测的输出是通过率而不是布尔值。

:::

::: details 追问 3：评测集会不会被"应试"——大家只优化这几十个用例？

会，经典的 Goodhart 风险。防护：评测集持续从线上回流新鲜用例（考题在变）；保留一个不公开给开发同学的 holdout 子集定期抽查；监控"评测分涨但线上指标没涨"的背离——那就是过拟合信号；文化上把评测定位为"防回归的地板"而不是"优化的天花板"，真正的优化目标始终是线上北极星指标。

:::
