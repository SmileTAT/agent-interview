# Agent 的可观测性：trace 应该记录什么？怎么用起来？

<QuestionMeta />

## 题目

"没有 trace 的 Agent 系统无法调试"已是共识。请说明 Agent trace 应该记录哪些内容、怎么组织，以及围绕它的使用场景。

::: details 参考答案

**记录什么——完整还原"模型当时看到了什么、做了什么"**：

1. **每次模型调用**：完整输入（系统提示版本号+消息序列）、完整输出（含思考/工具调用）、模型版本、采样参数、token 用量、延迟、缓存命中；
2. **每次工具执行**：工具名、入参、返回（或其摘要+完整内容的存储引用）、耗时、成败与错误；
3. **控制流事件**：委托子 Agent、压缩历史（压缩前后快照引用）、检索操作（查询与召回结果）、预算触发、人工确认点；
4. **业务锚点**：用户 ID（脱敏）、会话 ID、任务类型、最终结果状态、用户反馈。

**怎么组织**：树状 span 结构（一个任务一个 trace，Agent 循环每步一个 span，子 Agent 是子树）——直接复用 OpenTelemetry 语义约定的 GenAI 扩展，别自造轮子；大对象（长返回、文件）存对象存储、trace 里放引用，控制 trace 体积。

**关键细节：记录"看到的"而不只是"发生的"**——历史被压缩过的话，要能还原模型在第 N 步实际收到的上下文，否则调试时你看着完整历史说"信息明明在啊"，其实模型早就看不到了。

**使用场景（可观测性的四个消费方）**：

- **调试**：单 trace 回放定位失败步；
- **监控告警**：聚合指标——任务完成率、步数分布、工具失败率、成本/任务、延迟分位数，异常告警；
- **评测供给**：坏例从 trace 直接转成评测用例（输入输出都是现成的）；
- **产品分析**：用户在问什么、哪类任务完成率低——路线图的依据。

**答题关键**：四类记录项 + "还原模型视角"这个易漏点 + OTel 复用 + trace 是调试/监控/评测/分析四件事的共同底座。

:::

## 追问链

::: details 追问 1：trace 里有用户对话和业务数据，隐私合规怎么处理？

分级存储：trace 的**结构与指标**（步数、耗时、工具序列、成败）长期保留，**内容载荷**（对话原文、工具返回）短期保留+访问控制+按需脱敏（PII 检测打码）；用户删除请求要能级联到 trace 存储；调试时的"完整回放"权限收敛到 on-call 少数人并留审计。折中技巧：内容过期后保留 LLM 生成的脱敏摘要，让老 trace 仍可用于粗粒度分析。

:::

::: details 追问 2：全量记录成本太高（尤其是完整上下文快照），怎么取舍？

分层采样：**失败任务全量记录**（调试价值最高）、成功任务按比例采样、护栏触发/高成本/长尾延迟的任务强制全量。上下文快照用**增量存储**——消息本身已按 append 记录，只需记"压缩/修改事件"的 diff 即可重建任意步的视图，不必每步存全量。经验上失败全量+成功抽样能砍掉大部分存储成本而几乎不损失调试能力。

:::

::: details 追问 3：有了 trace，怎么从"被动调试"走向"主动发现问题"？

在 trace 流上跑持续分析：**模式检测**——重复调用、步数异常、工具连续失败等反模式自动标记；**漂移监控**——任务类型分布、平均步数、缓存命中率的周环比漂移告警（用户行为或上游模型变化的早期信号）；**抽样质检**——每天从成功任务中抽样送 LLM-as-Judge 复核，抓"看起来成功其实答错"的静默失败。目标状态：多数问题由系统先于用户投诉发现。

:::
