# 为什么 Agent 评测要看轨迹而不仅是最终答案？如何落地轨迹级评测？

<QuestionMeta />

## 题目

评测一个 Agent 时，只看最终答案的正确率有什么问题？请说明轨迹级评测（trajectory evals）的必要性和落地方法。

::: details 参考答案

**只看最终答案的三个盲区**：

1. **过程危险，结果正确**：Agent 可能靠越权操作、误打误撞拿到正确答案——结果指标看不出它删过不该删的数据、调过不该调的接口；
2. **过程低效，结果正确**：15 次工具调用完成本应 3 次完成的任务，结果分相同，成本差 5 倍；线上放大后就是延迟和账单事故；
3. **无法归因**：答案错了，是检索错、工具错、还是最后一步生成错？端到端分数无法指导优化方向。

**轨迹级评测的落地方法**：

- **步骤级断言（确定性检查）**：对已知场景写规则——"必须先调用身份验证工具再查订单""不允许出现删除类操作""工具调用次数 ≤ N"。便宜、稳定，适合做 CI 门禁；
- **轨迹质量评审（LLM-as-Judge）**：把完整轨迹（含 Thought、工具调用、观察）交给强模型按 rubric 打分：目标对齐度、工具选择合理性、无效步骤占比、错误恢复能力。适合开放场景，但要做校准（见追问）；
- **关键节点标注**：人工标注 golden 轨迹的关键决策点（该在第几步调什么工具），对比实际轨迹的决策一致率；
- **代价指标**：步数、token、延迟、失败重试率——作为质量分的约束项一起报告。

**工程闭环**：线上轨迹全量采集（trace）→ 抽样评审 + 告警（如工具失败率突增）→ 坏例沉淀进回归集 → 每次改动（换模型/改提示/加工具）跑回归集防劣化。

**答题关键**：结果指标与过程指标是互补而非替代；轨迹评测的最终价值是让"改一版提示词"从玄学变成有回归保障的工程活动。

:::

## 追问链

::: details 追问 1：LLM-as-Judge 评轨迹靠谱吗？有哪些已知偏差，怎么校准？

已知偏差：**偏长**（更长的轨迹/答案得分偏高）、**位置偏差**（成对比较时偏向先出现的）、**自我偏好**（judge 偏爱与自己同源模型的输出风格）、**对表面流畅的过度奖励**。校准方法：抽样人工双标，计算 judge 与人类的一致率（目标通常 >80% 才可用）；rubric 写成可验证的具体条目而不是"整体质量 1-10 分"；成对比较时交换顺序跑两遍取一致结果；定期用人工标注回测 judge 漂移。

:::

::: details 追问 2：回归集怎么建？Agent 的环境是动态的（工具返回会变），怎么保证可复现？

两层：**录制回放**——把真实会话的工具返回录下来，回归时 mock 工具用录制结果回放，隔离环境变化，专测模型决策；**沙箱环境**——为核心场景搭建确定性的模拟环境（固定的知识库快照、可重置的测试账号），测端到端。回归集来源：线上坏例（每个修过的 bug 必入集）+ 高频场景采样 + 对抗构造（边界输入）。注意用例要标注"考察点"，失败时能直接看出退化在哪类能力。

:::

::: details 追问 3：线上没有标准答案，怎么持续监控 Agent 质量？

用**代理指标 + 抽样评审**组合：硬指标（任务完成率——如客服场景的"未转人工且用户未追问"、工具失败率、平均步数、超时率、用户显式反馈）做实时告警；在此之上每日抽样送 LLM-as-Judge 打分，周级人工复核校准。重点监控**分布漂移**：新型用户问题、工具返回格式变化、模型供应商静默更新——这三个是线上 Agent 劣化的最常见外因。

:::
