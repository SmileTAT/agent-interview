# 多 Agent 之间的上下文传递为什么容易丢信息？怎么设计交接？

<QuestionMeta />

## 题目

多 Agent 系统最常见的失败不是某个 Agent 能力不足，而是 Agent 之间"没对齐"。请分析上下文传递的丢失机制和交接设计方法。

::: details 参考答案

**丢失机制——每次委托都是一次有损压缩**：主 Agent 给子 Agent 下任务时，要把自己上下文中的相关信息**转述**成任务描述；子 Agent 完成后又把过程**压缩**成结论返回。两次转述都由模型完成，都会丢失：

- **隐性约束丢失**：主 Agent 知道"用户要的是国内方案"，下发任务时没写，子 Agent 调研了一堆海外方案；
- **背景语境丢失**：子 Agent 不知道任务的"为什么"，在歧义处做出与全局目标相悖的局部合理选择；
- **返回时的证据丢失**：子 Agent 报告"方案 A 可行"，但支撑判断的关键前提没带回来，主 Agent 无法校验。

**交接设计——把"转述"变成"结构化契约"**：

**下行（任务委托书）**，模板化强制包含：任务目标与验收标准、**已知约束全集**（预算/范围/格式/禁忌）、必要背景（任务在全局中的位置、为什么做）、可用资源与边界（能用什么工具、不能碰什么）、预算（步数/时间）。

**上行（结果报告书）**，约定输出 schema：结论、关键证据与前提、置信度与未决问题、过程产物的引用（完整内容放共享存储）。

**共享底座**：与其靠每次转述，不如让稳定的全局信息（用户原始需求、全局约束、术语表）放在**共享上下文区**，所有 Agent 都注入同一份——转述只负责任务特定部分，全局部分不经转述。

**答题关键**："委托即有损压缩"的机制认知 + 双向结构化契约 + 共享底座减少转述面。

:::

## 追问链

::: details 追问 1：怎么发现系统里存在交接丢失问题？有什么诊断信号？

轨迹上的典型信号：子 Agent 的产出被主 Agent 频繁**返工**（"不是这个意思，重做"占比高）；子 Agent 在任务中途向主 Agent 反问本应随任务下发的信息；最终结果违反了用户在主对话早期提出的约束（约束没传下去）。定量做法：抽样评审"委托书完备率"——对照约束全集检查任务描述漏了几条，这是多 Agent 系统质量审计的固定项目。

:::

::: details 追问 2：子 Agent 能不能直接读主 Agent 的完整上下文，彻底避免转述丢失？

技术上可以但通常不该：完整上下文里大量信息与子任务无关，稀释子 Agent 的注意力（相当于放弃了多 Agent 最大的收益——上下文隔离）；且成本翻倍。折中方案：主 Agent 上下文的**结构化部分**（约束清单、用户原始需求）直接共享，过程性对话不共享；或给子 Agent 一个"查询主上下文"的工具，按需拉取而不是全量继承。

:::

::: details 追问 3：交接契约模板会不会太重？简单任务也要填一堆字段？

契约的粒度应随任务风险分级：一次性的只读小任务（查个天气）用轻量委托（一句话+输出格式）；多步、有副作用、或结果将被下游依赖的任务才用完整契约。工程上把契约做成委托工具的参数 schema——必填字段就是强制字段，模型填不出"约束全集"时这本身就是个信号（说明主 Agent 自己也没想清楚约束）。模板不是官僚主义，是把隐性失误显性化的手段。

:::
