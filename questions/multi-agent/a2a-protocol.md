# A2A 协议解决什么问题？和 MCP 是什么关系？

<QuestionMeta />

## 题目

请解释 A2A（Agent2Agent）协议的定位与核心机制，并说明它与 MCP 的分工关系。

::: details 参考答案

**A2A 解决的问题**：跨团队、跨厂商、跨框架的 **Agent 之间互操作**。企业里的 Agent 会由不同供应商构建（HR 系统的 Agent、财务 SaaS 的 Agent、自研 Agent），没有标准协议时它们无法互相发现和协作。A2A（Google 2025 年发起的开放协议，后捐赠给 Linux 基金会）为此定义了统一的通信标准。

**核心机制**：

1. **Agent Card**：每个 Agent 发布一份"名片"（JSON 元数据），声明自己的能力（skills）、端点、认证方式——解决**发现**问题；
2. **任务（Task）为中心的交互**：客户端 Agent 向远端 Agent 提交任务，任务有生命周期状态（提交/进行中/需要输入/完成/失败），支持长时任务的异步执行与进度更新（轮询/SSE/推送）——这与"一问一答"的函数调用有本质区别，Agent 间协作往往是长时程的；
3. **不透明协作**：双方只交换任务与产物（artifacts），**不暴露内部实现**（内部提示、工具、推理过程）——这对跨组织协作至关重要（商业与安全边界）。

**与 MCP 的分工**（互补不竞争）：

- **MCP**：Agent ↔ 工具/资源——把外部能力接入一个 Agent，纵向集成；
- **A2A**：Agent ↔ Agent——对等实体间的任务协作，横向互操作；
- 一句话类比：MCP 给 Agent"接上手脚"，A2A 让 Agent 之间"打电话谈业务"。一个 Agent 完全可以同时用 MCP 接工具、用 A2A 委托别家 Agent。

**答题关键**：互操作定位 + 三个机制（发现/任务生命周期/不透明性）+ 与 MCP 纵横分工。

:::

## 追问链

::: details 追问 1：既然子 Agent 可以包装成"工具"被调用，为什么还需要 A2A？把远端 Agent 做成 MCP 工具不行吗？

同组织内确实常这么做（agent-as-tool）。A2A 的增量价值在跨边界场景：**长时任务的生命周期管理**（工具调用是同步短事务模型，A2A 任务可以跑几小时并汇报进度、中途要补充输入）；**对等协商语义**（远端 Agent 可以反问澄清，而工具只能成功或失败）；**跨组织的发现与认证标准**。简单说：内部协作用 agent-as-tool 够了，跨厂商、长时程、需要标准化发现的场景才需要 A2A。

:::

::: details 追问 2：调用一个外部厂商的 A2A Agent，信任问题怎么处理？

三层：**身份与授权**——Agent Card 的认证声明 + 企业侧的准入白名单（哪些外部 Agent 可被委托、可委托什么类别任务）；**数据边界**——委托任务时最小化披露（只给任务必需的数据），敏感数据不出域；**结果不可信原则**——外部 Agent 的返回视为不可信输入（与网页内容同级），进主流程前过校验，据此执行写操作要额外确认。本质上把"供应链安全"思维搬到 Agent 协作上。

:::

::: details 追问 3：A2A 的不透明性（看不到对方内部过程）对调试和评测是不是灾难？

确实是代价：跨组织排障从"看轨迹"退化为"看任务交互记录"。缓解：A2A 交互本身要完整留痕（任务描述、状态变迁、中间消息、产物），作为双方对账的依据；给外部 Agent 建立**黑盒评测**——用标准任务集定期探测其质量与延迟，纳入 SLA；关键链路设兜底（外部 Agent 质量劣化时切换备选或收回自营）。这和依赖第三方 API 的治理逻辑一致，只是对象从 API 变成了 Agent。

:::
