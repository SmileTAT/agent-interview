# 什么时候需要多 Agent？什么时候单 Agent 更好？

<QuestionMeta />

## 题目

多 Agent 架构听起来先进，但也带来复杂度。请给出多 Agent vs 单 Agent 的选型判断。

::: details 参考答案

先破除误区：**多 Agent 不是能力升级，而是一种有代价的架构拆分**。默认答案应该是单 Agent，多 Agent 需要论证。

**真正需要多 Agent 的三类理由**：

1. **上下文隔离**：子任务的过程信息量巨大但结论短小（并行搜索、大规模文件分析），拆出去跑可以保护主上下文——这是当前最站得住的理由，本质是上下文工程手段；
2. **关注点冲突**：一个 Agent 内难以兼顾的角色需要分离——生成者与评审者（critic 独立才客观）、执行者与安全审查者；权限隔离也属此类（高权限工具只给受控的专职 Agent）；
3. **天然并行的任务结构**：多个子任务互不依赖（同时调研 5 个竞品），并行子 Agent 换时间。

**伪需求警报**：

- "按人类部门划分 Agent"（产品 Agent + 开发 Agent + 测试 Agent 开会）——拟人化架构，通信开销巨大而收益存疑；
- 单 Agent 提示写不好就想拆多 Agent——拆分不解决提示问题，只会把它复制 N 份再加上通信问题。

**多 Agent 的固有代价**：上下文传递必然有损（见 handoff 一题）、错误跨 Agent 传播难归因、成本倍增（每个 Agent 都携带自己的上下文）、系统行为方差变大。

**判断顺口溜**：**为隔离而拆、为并行而拆、为权限而拆，不为"分工好听"而拆。**

**答题关键**：默认单 Agent 的克制 + 三个正当理由 + 识别拟人化伪需求。

:::

## 追问链

::: details 追问 1：怎么用数据验证"拆成多 Agent 是值得的"？

和所有架构决策一样 A/B：同一评测集上对比单 Agent（配好的上下文管理）vs 多 Agent 版的完成率、端到端延迟、总 token 成本、失败归因难度。特别注意公平性：单 Agent 基线要认真调优（很多"多 Agent 更好"的结论其实是单 Agent 基线没做好上下文管理）。收益不能覆盖成本与复杂度增量的，回退单 Agent。

:::

::: details 追问 2：主 Agent + 子 Agent（orchestrator-worker）算多 Agent 吗？它为什么是最常见的形态？

算，而且是最克制的形态：控制流仍集中在主 Agent（单点决策、好调试），子 Agent 只是"带上下文隔离的函数调用"——领任务、干活、交结论，不参与全局决策，子 Agent 之间不互相通信。它规避了对等多 Agent 最难的问题（去中心化协调、循环委托），保留了隔离与并行的收益。绝大多数生产场景走到这一层就够了。

:::

::: details 追问 3：多个对等 Agent 自由讨论（debate/群聊模式）有实用价值吗？

辩论模式在研究里对部分推理任务有增益，但生产中要小心：多轮互评的 token 成本高，且容易出现"表面共识"（互相附和）或无休止分歧。实用的收敛做法是把它退化为结构化流程：生成 → 独立评审（不看彼此）→ 汇总裁决，一轮完成——这其实又回到了 Workflow。让多个 Agent 开放式聊天在绝大多数生产场景是成本黑洞，面试中表达这个判断本身就是加分项。

:::
