# 什么是 Prompt/KV 缓存？Agent 应用怎么围绕它优化成本和延迟？

<QuestionMeta />

## 题目

主流大模型 API 都提供 Prompt Caching，缓存命中的部分价格和延迟大幅下降。请解释原理，并说明 Agent 应用该怎么设计上下文来吃到这个红利。

::: details 参考答案

**原理**：Transformer 推理时,每个 token 的 Key/Value 张量只依赖它前面的内容。如果两次请求共享**完全相同的前缀**,前缀部分的 KV 张量可以缓存复用,免去重算——这就是 Prompt Caching。命中部分的输入价格通常降到原价的 1/10 左右,首 token 延迟也显著下降。

**关键约束：前缀必须逐字节相同**。前缀中任何一处变动,该位置之后的缓存全部失效。

**Agent 场景为什么特别受益**：Agent 循环每一轮都携带全部历史重新请求,第 N 轮的前缀恰好是第 N-1 轮的内容——天然的高命中场景,前提是你别破坏它。

**围绕缓存的上下文设计守则**：

1. **稳定内容前置,易变内容后置**：系统提示、工具定义放最前且冻结;会话级动态信息（当前时间、用户状态）放在稳定块之后;
2. **不要在前缀里埋"每次都变"的东西**：系统提示里放精确到秒的时间戳、随机 ID、动态排序的工具列表,都是缓存杀手;
3. **追加式更新历史**：新消息永远 append,不要回头修改/重排历史消息;
4. **压缩与缓存的权衡**：滚动压缩会改写历史导致缓存失效,水位线和压缩幅度要考虑这笔账（见上下文溢出一题）;
5. **工具集稳定**：运行中途动态增删工具定义会打掉后续缓存,按需挂载工具要放在设计好的边界点。

**监控**：把缓存命中率（cached tokens / input tokens）做成核心成本指标,Agent 应用健康值通常应很高,命中率突降常意味着有人在前缀里加了动态内容。

**答题关键**：前缀逐字匹配的机制 + "稳定前置、易变后置、只追加"三守则 + 命中率监控。

:::

## 追问链

::: details 追问 1：多副本部署的网关随机路由，自建推理服务的 KV Cache 命不中，怎么办？

缓存在实例内存/显存里,请求换了实例自然不命中。方案是**会话亲和路由**：按会话 ID 一致性哈希到固定实例,同一 Agent 会话的连续轮次落到同一副本。推理框架（如 vLLM 的 prefix caching）配合亲和路由才能发挥;更进一步有分布式 KV Cache 方案（缓存外置/跨实例共享）,但复杂度高,先把亲和路由做对通常就够了。

:::

::: details 追问 2：系统提示里确实需要当前日期，怎么放才不炸缓存？

降低精度和更新频率：日期到"天"而不是秒,当天之内前缀就稳定;或者把时间信息从系统提示挪到最新一条用户消息附近（后置）,前缀完全不受影响。通用原则：任何动态信息先问三个问题——模型真的需要吗、能不能降低变化频率、能不能后置。

:::

::: details 追问 3：并行跑 100 个同类 Agent 任务，怎么利用缓存省钱？

让它们共享尽量长的公共前缀：系统提示+工具定义+共享的任务背景完全一致（逐字节）,只有任务特定输入放在末尾。第一个请求建立缓存,后续 99 个命中公共前缀。工程上注意：并发首发会导致缓存未建立时的竞争,可以先发一个"预热"请求再放量;不同 API 的缓存有 TTL 和最小长度门槛,批任务调度要让同前缀请求在时间上聚集。

:::
