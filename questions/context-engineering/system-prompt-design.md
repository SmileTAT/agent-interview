# Agent 的系统提示应该放什么、不放什么？怎么组织？

<QuestionMeta />

## 题目

生产 Agent 的系统提示动辄几千 token，且往往越改越臃肿。请说明系统提示的内容取舍原则和组织方法。

::: details 参考答案

**该放的（系统提示的本职）**：

1. **角色与任务边界**：是谁、为谁服务、能做什么、明确不做什么；
2. **跨任务稳定的行为规则**：输出规范、语气、安全红线、终止条件、"不确定时怎么办"的元规则；
3. **环境说明**：模型无法自行感知的事实（部署环境、可用资源的约定、当前日期粒度到天）；
4. **工具使用的全局策略**：优先级约定（"退款直接用 process_refund"）、必须/禁止的调用模式。

**不该放的**：

- **任务特定信息**：属于用户消息或任务层，放系统提示里会污染所有会话；
- **大段知识库内容**：应该走检索按需注入——系统提示不是知识的家；
- **能用工具/代码保证的事**：格式校验、权限控制写在系统提示里只是"求模型配合"，应下沉到工程层；
- **针对个别 bad case 的补丁堆积**：每次出问题就加一条"注意不要 X"，最终得到一份互相冲突的补丁集——正确做法是归因后修根源（工具描述、流程设计），提示只留普适规则。

**组织方法**：分节+标题（角色/规则/工具策略/输出格式），机器和人都好维护；规则按优先级排列并说明冲突时的裁决顺序；用简洁的祈使句，删除冗余的礼貌性铺垫；**版本化管理**——系统提示进代码库，每次改动跑评测回归，和代码同等待遇。

**臃肿治理**：定期审计每条规则——"删掉它评测会掉吗？"掉才留。很多规则是历史遗留，模型早已不需要。

**答题关键**：稳定性作为取舍标准（只放跨任务稳定的内容）+ "补丁堆积"反模式 + 提示即代码的工程化管理。

:::

## 追问链

::: details 追问 1：规则写了模型不遵守，加重语气（"必须！！"）有用吗？正确的调试方法是什么？

加重语气偶尔有短期效果但不可靠，且会陷入军备竞赛。正确调试：先看轨迹确认模型"没看到"还是"看到但没执行"——前者是上下文问题（规则被稀释/太靠中间），把规则前移、精简周边内容；后者检查规则本身是否含糊、与其他规则冲突、或与任务激励相悖（要求详尽又要求简短）。仍不行就别靠提示了：能硬约束的下沉到结构化输出/工具层校验。

:::

::: details 追问 2：多个业务共用一个 Agent 底座，系统提示怎么支持定制又不失控？

分层拼装：底座层（通用角色、安全红线、工具策略）+ 业务层（各业务自己的规则）+ 会话层（用户偏好），运行时按序拼接。治理要点：底座层由平台团队独占修改权并全量回归；业务层有 token 配额和禁止事项（不得覆盖安全红线）；拼装顺序固定且冲突裁决规则明确（底座优先）。这本质上是把系统提示当成有权限模型的配置系统来管理。

:::

::: details 追问 3：系统提示的 A/B 评测怎么做才靠谱？

难点是提示改动的影响面广且有随机性。做法：固定评测集（覆盖主要任务类型+历史 bad case 回归）+ 每用例多次采样看分布而不是单次结果；指标分维度（任务完成率/规则遵守率/token 成本）避免单指标掩盖劣化；线上再灰度小流量对比真实指标。最重要的纪律：**一次只改一个语义单元**，大重写要拆成可归因的小步。

:::
