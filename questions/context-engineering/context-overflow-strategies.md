# 长任务把上下文窗口打满了怎么办？说说你的处理策略

<QuestionMeta />

## 题目

Agent 执行长任务（几十轮工具调用）时上下文持续膨胀，最终溢出。请系统说明处理策略及各自的取舍。

::: details 参考答案

按侵入性从低到高，四类策略通常组合使用：

**1. 源头减量（最优先）**
工具返回裁剪与分页、大文件只读相关片段、检索结果限量——不让垃圾进来，比事后压缩有效得多。很多"上下文不够"的系统，一查全是没裁剪的工具返回。

**2. 滚动压缩（compaction）**
达到水位线（如 80%）时,把较早的对话与工具观察**摘要替换**：保留任务目标、关键决策及理由、当前状态、未决事项,丢弃过程性细节。要点：最近 N 轮保持原文（近期信息对决策最重要）;摘要用结构化模板而不是自由发挥,降低信息丢失的随机性。

**3. 结构化外置（笔记/暂存区）**
把状态写到上下文之外的持久层：任务清单文件、进展笔记、中间产物存文件系统,上下文里只留索引("详细调研结果见 notes/research.md"),需要时再读回。这把"记住"变成了"可检索",是长任务最扎实的方案——上下文成为工作台而非仓库。

**4. 子任务隔离（sub-agent）**
把大块独立工作交给子 Agent 在独立上下文中完成,只把结论返回主上下文。搜索、批量文件分析这类"过程庞大、结论短小"的工作最适合。

**取舍意识**：压缩必有信息损失,风险是"摘要丢了后面才需要的细节"——所以外置（可找回）优于压缩（不可找回）,压缩优于截断（无差别丢弃）。截断是最后手段且应丢中间保首尾。

**答题关键**：先减量再压缩、外置优于压缩优于截断、水位线机制、子 Agent 隔离。

:::

## 追问链

::: details 追问 1：压缩摘要丢掉了后面需要的细节，怎么发现和补救？

发现：轨迹评测中构造"回马枪"用例——任务后段需要引用前段细节,考察压缩后是否答错;线上监控"用户纠正率"（用户说"我之前说过X"）。补救：压缩时不删原文,原始轨迹落盘,摘要里带引用锚点("第 12 轮的完整报错见 trace"),配一个"回查历史"的工具让模型能主动找回;关键实体（ID、路径、数字）在摘要模板里强制保留——细节丢失多发生在这类硬信息上。

:::

::: details 追问 2：滚动压缩会破坏 KV Cache 吗？怎么权衡？

会——压缩改写了历史消息,此前的缓存前缀全部失效,下一轮要全量重算。所以压缩频率是"token 节省"与"缓存失效成本"的权衡：水位线不要设太低（频繁压缩两头吃亏）,一次压缩要压得足够多（腾出大空间,摊薄这次失效成本）,并把压缩时机对齐到任务阶段边界（阶段切换处本来就有上下文重组需求）。

:::

::: details 追问 3：多长算"该用子 Agent 隔离"？给个判断方法。

看"过程/结论比"：一段工作的中间过程 token 是最终有用结论的很多倍（比如翻 30 个网页得出 3 段结论、扫全仓库代码定位 1 个函数）,就该隔离——主上下文只需要结论。反之,过程本身对后续决策有持续价值的（每一步都可能被回看的调试过程）不适合隔离,隔了反而丢上下文。另一个信号：这段工作与主线程的交互只有"进去一个问题、出来一个答案",接口越窄越适合隔离。

:::
