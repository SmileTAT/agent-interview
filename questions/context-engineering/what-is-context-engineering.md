# 什么是上下文工程？它和提示工程的区别在哪？

<QuestionMeta />

## 题目

"上下文工程（Context Engineering）"被认为是继提示工程之后 Agent 开发的核心技能。请解释它的内涵，以及与提示工程的区别。

::: details 参考答案

**定义**：上下文工程是对**进入模型上下文窗口的全部信息**进行选择、组织和维护的工程实践——目标是在有限的上下文预算内，让模型在每一步都恰好看到"完成当前决策所需的最小充分信息集"。

**与提示工程的区别**：

| | 提示工程 | 上下文工程 |
|---|---------|-----------|
| 对象 | 指令文本怎么写 | 整个上下文放什么、不放什么 |
| 时机 | 主要在设计期写死 | 大量决策发生在**运行时**（动态检索、压缩、丢弃） |
| 典型问题 | "怎么措辞让模型遵循格式" | "20 轮工具调用的观察结果留哪些？工具定义全量注入还是检索注入？" |
| 场景 | 单轮任务为主 | 多轮长程 Agent 的核心问题 |

可以说提示工程是上下文工程的子集：当系统变成长程 Agent，上下文的主要成分不再是人写的提示，而是**动态累积的**历史消息、工具定义、工具返回、检索内容、记忆——管理这些动态成分才是难点。

**为什么重要——上下文不是越多越好**：注意力是稀缺资源，无关信息会稀释关键信息（context rot / lost in the middle 现象）；长上下文直接推高成本与延迟。所以上下文工程的日常是在做减法：压缩历史、裁剪工具返回、按需检索而非全量堆放。

**核心手段速览**：系统提示分层组织、工具返回裁剪与摘要、对话历史滚动压缩、检索式注入（记忆/知识/工具定义按需加载）、长任务的结构化笔记（把状态写到上下文外的持久层）。

**答题关键**："最小充分信息集"这个目标 + 静态设计与运行时管理的区分 + "做减法"的直觉。

:::

## 追问链

::: details 追问 1："无关信息稀释注意力"有什么实际证据？给个工程上能感知的例子。

典型例子：给 Agent 挂 50 个工具（全量注入定义）后,原本稳定的工具选择开始出错,砍到 15 个相关工具后恢复——工具定义之间互相干扰。又如长对话里模型"忘记"了早期的关键约束，其实约束还在窗口内，只是被大量中间内容稀释（lost in the middle：模型对上下文中部信息的利用率明显低于首尾）。这也是为什么关键约束要放系统提示（头部）并在必要时重申。

:::

::: details 追问 2：上下文预算怎么分配？给一个大致的框架。

按稳定性分层：**稳定层**（系统提示+工具定义,可缓存,应尽量不变）、**任务层**（当前任务描述、关键中间结论）、**滚动层**（近期对话与工具观察,可压缩淘汰）、**按需层**（检索来的知识/记忆,用完即弃）。分配原则：稳定层精简且冻结（为了 KV Cache 命中）,滚动层设水位线触发压缩,按需层控制单次注入量。具体比例依任务而定,但"稳定层冻结"和"滚动层有水位线"是通用的。

:::

::: details 追问 3：怎么评测上下文工程做得好不好？

三组指标：**质量**——同一评测集上,上下文策略 A/B 的任务完成率（好的压缩不应掉点）；**效率**——平均每任务 token 消耗、KV Cache 命中率、首 token 延迟；**长程稳定性**——专门构造需要 30+ 轮的长任务,考察后段是否出现"忘记约束/重复劳动/引用错误"。常见反直觉结论：激进压缩省了 token 但完成率掉了,总成本反而升——所以一定要质量和效率一起看。

:::
