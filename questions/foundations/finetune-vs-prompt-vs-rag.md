# 微调、提示工程、RAG 怎么选？给出决策框架

<QuestionMeta />

## 题目

让模型适配业务有三条路：提示工程、RAG、微调。请给出选型决策框架，并纠正常见误区。

::: details 参考答案

**按"你要改变模型的什么"来分工**：

- **提示工程/上下文工程**：改变**行为方式**——角色、格式、流程、少样本模仿。零训练成本、分钟级迭代、随基座升级免费受益。**永远是第一步**；
- **RAG**：改变**可用知识**——模型没见过的、变化快的、需要溯源的事实（企业文档、实时数据）。知识更新=更新索引，不动模型；天然支持引用与权限过滤；
- **微调（全参/LoRA）**：改变**内化能力**——稳定的风格/格式一致性、领域语言的流利度、特定任务的可靠性（分类、抽取），以及**小模型学会大模型示范的行为**（蒸馏降本）。

**决策顺序（不是三选一，是叠加的漏斗）**：

```
1. 提示做到位了吗？（含 few-shot、结构化约束）→ 大多数需求止步于此
2. 问题是"缺知识"？→ RAG（微调灌知识既贵又易过时且难溯源——经典反模式）
3. 问题是"行为不稳定/风格不一致/成本太高"且有量、有数据？→ 微调
```

**常见误区纠正**：

1. **"微调能让模型记住我们的知识"**——效率极低且无法及时更新、无法引用出处，知识类需求 99% 该用 RAG；
2. **"RAG 和微调二选一"**——常见的最优解是组合：微调教会"怎么用检索结果的行为范式"，RAG 供给事实；
3. **低估微调的隐性成本**——不止训练费：数据构建与清洗、评测防回退（微调可能损伤通用能力）、基座升级后重训的持续负担；
4. **跳过提示直接微调**——没把提示调到位就微调，等于用最贵的手段修最便宜的问题。

**答题关键**：行为/知识/能力的分工、漏斗顺序、"微调灌知识"反模式、组合思维。

:::

## 追问链

::: details 追问 1：什么信号说明"该微调了"？

同时满足三条：**提示已到收益天花板**（few-shot、结构化都试过，指标卡住）；**问题模式是行为类的**（格式偶发漂移、风格不稳、特定任务错误率高，而不是缺知识）；**有数据有量**（几百~几千条高质量示例可得，且调用量大到能摊销训练与维护成本）。典型正当场景：高频结构化任务用 LoRA 调小模型替代大模型（延迟成本降一个量级）、领域术语密集场景的语言适配、蒸馏。

:::

::: details 追问 2：LoRA 和全参微调怎么选？

LoRA（低秩适配）冻结原权重、只训少量低秩增量矩阵：显存与算力需求大降、产物小（可多任务热切换 adapter）、灾难性遗忘更轻——**应用团队的默认选择**。全参微调上限更高，但需要的数据、算力、评测保障都上一个量级，一般属于有训练基建的团队做深度领域模型时的选项。实践顺序：LoRA 起步，确认收益后再评估是否值得全参。（QLoRA 进一步用量化压显存，消费级卡也能调中等模型。）

:::

::: details 追问 3：微调后模型"变笨了"（通用能力下降）怎么办？

这是灾难性遗忘/对齐损伤，预防大于治疗：训练数据里**混入通用数据**（不只灌领域样本）；用 LoRA 且控制训练强度（epoch、学习率）；评测集必须同时包含**领域任务和通用能力回归项**（指令遵循、安全性），只盯领域指标就会"练成偏科"。已经发生的话：回退检查点、降训练强度重训；或干脆收窄微调模型的使用范围（只在特定任务路由到它，通用对话仍走基座）——专模专用本来就是合理架构。

:::
